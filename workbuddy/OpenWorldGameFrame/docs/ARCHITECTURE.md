# 开放世界游戏服务端框架 · 设计说明

> 技术栈：Go 1.22+ ｜ 目标形态：无缝大世界、分区分服、可水平扩展
> 状态：v0.1 骨架设计，未实现

---

## 一、先定三件事

开放世界服务端的复杂度不来自"玩法多"，而来自三个约束互相打架：

| 约束 | 具体表现 | 设计代价 |
|---|---|---|
| 无缝 | 玩家跨区域不能读条、不能掉线 | 实体迁移必须在线完成 |
| 大世界 | 同时在线万级，实体十万级 | 单进程扛不住，必须分区 |
| 强一致 | 位置、血量、归属不能各说各话 | 同一实体的写操作必须串行 |

结论：**空间分区 + 单写者模型**。这是所有设计决策的源头，后面每个模块都是从这两条推出来的。

## 二、进程拓扑

```
                    ┌──────────────┐
   客户端 ──TCP/KCP──│  Gate × N    │  只做连接、编解码、转发，无游戏逻辑
                    └──────┬───────┘
                           │ 内部 RPC
              ┌────────────┼────────────┐
        ┌─────▼─────┐┌─────▼─────┐┌─────▼─────┐
        │ World #1  ││ World #2  ││ World #3  │  各管一片区域，
        │ Scene×M   ││ Scene×M   ││ Scene×M   │  互不共享内存
        └─────┬─────┘└─────┬─────┘└─────┬─────┘
              └────────────┼────────────┘
                    ┌──────▼───────┐
                    │  Data 层     │  Redis + MySQL
                    └──────────────┘
```

**为什么 Gate 和 World 分开**：客户端连接是长连接、数量大、逻辑极轻；世界逻辑重 CPU、要频繁 tick。混在一起会导致一次 GC 停顿踢掉一片连接。分开后 Gate 可以独立扩容，World 可以独立滚动更新。

**Scene 不是进程，是 World 进程内的一个 Actor**。一个 World 进程跑 20~50 个 Scene，每个 Scene 一个 goroutine。这样既避免了进程间通信开销，又能通过加 World 进程水平扩展。

## 三、并发模型（最关键的一节）

### 3.1 单写者原则

一条铁律：**同一个实体，同一时刻只有一个 goroutine 能写它。**

Go 里最容易犯的错是给每个 Entity 开一个 goroutine 加锁，几万个实体就是几万个 goroutine 抢锁，调度器直接崩。正确做法是把粒度放大到 Scene：

```go
// 一个 Scene 一个主循环，所有实体逻辑都在这个 goroutine 里串行执行
func (s *Scene) Run(ctx context.Context) {
    ticker := time.NewTicker(50 * time.Millisecond) // 20Hz
    defer ticker.Stop()
    for {
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
            s.doTick(s.frame)      // 逻辑帧：AI、移动、Buff、战斗结算
            s.flushAOI()           // 视野事件批量下发
            s.frame++
        case msg := <-s.mailbox:   // 外部消息（玩家操作、跨场景事件）
            s.handle(msg)          // 在同一个 goroutine 里处理，天然无锁
        }
    }
}
```

好处：
- 实体数据不需要任何锁，纯结构体读写，CPU cache 友好
- 逻辑是确定性的，回放和压测都好做
- 单个 Scene 内不会出现竞态，调试成本大幅下降

代价：单 Scene 有性能上限（实测一个 goroutine 每秒能处理百万级实体简单逻辑，足够）。超了就拆 Scene。

### 3.2 跨 Scene 通信只能是异步消息

Scene A 想让 Scene B 做某事，不能直接调方法，只能投递消息：

```go
type Message struct {
    From    SceneID
    To      SceneID
    Payload any        // 具体指令
    Reply   chan<- any // 需要回执时带上，nil 表示不关心结果
}
```

这条约束保证了：任何跨边界调用都不会造成两个 Scene 互相等待而死锁。

### 3.3 ECS 的定位

ECS 在这里**不是并发模型，是内存布局优化**。组件按类型连续存储，遍历时 cache 命中率高：

```go
type Pool[T any] struct {
    sparse []int32   // 实体 ID -> dense 下标
    dense  []T       // 连续存放的组件
    ids    []uint64
}
```

不要把 ECS 理解成"每个 System 一个线程并行跑"——那套在服务端会引入大量同步开销，得不偿失。本项目的所有 System 都**串行跑在同一个 tick 协程里**，按 `Command → Input → Logic → Replicate` 四个阶段排序（见 6.6）。并行化的是"多个场景"，不是"一个场景里的多个 System"。

## 四、功能模块清单

### 4.1 接入层 `internal/net` `internal/gate`

| 模块 | 职责 | 要点 |
|---|---|---|
| Conn | 连接生命周期、读写分离 | 读一个 goroutine、写一个带缓冲的 channel，避免阻塞 |
| Codec | 帧编解码 | 长度前缀 + 消息 ID + Protobuf body |
| Transport | TCP / KCP / WebSocket 可插拔 | 接口抽象，MMO 用 KCP 抗弱网，Web 端用 WS |
| Limiter | 每连接令牌桶 | 防刷包，超限直接断开 |
| Auth | 握手鉴权 | token 校验后才知道是哪个玩家 |
| Router | 消息路由到对应 World | 维护 sessionID → worldNode 的映射 |

网络层选型建议：**gnet 或 netpoll**（基于 epoll 的事件循环），不要用标准库 net 的一连接两 goroutine 模型，连接数上万后内存和调度开销都偏高。

### 4.2 世界拓扑 `internal/world`

负责"世界长什么样"以及"谁管哪块"。

| 模块 | 职责 |
|---|---|
| Topology | 世界坐标系、Chunk 划分（建议 64×64 米一格） |
| Allocator | Chunk → World 进程的分配表，支持一致性哈希便于扩缩容 |
| Registry | 全局实体归属表：entityID → sceneID，落地在 Redis |
| Handover | 跨 Chunk 迁移的握手流程（见 6.2） |

### 4.3 场景运行时 `internal/scene`

| 模块 | 职责 | 要点 |
|---|---|---|
| Scene | 实体容器 + tick 循环 | 一个 goroutine 独占 |
| EntityManager | 创建/销毁/查询 | ID 用 uint64，高 16 位放类型 |
| Scheduler | 定时器、延时任务 | 最小堆 + 帧号，不要用 time.After 满天飞 |
| Snapshot | 帧末状态快照 | 用于视野 diff 和回放 |

### 4.4 空间与视野 `internal/aoi`

这是开放世界最核心的模块，直接决定带宽和 CPU。

**两级分区**：

```
Chunk（64m，跨进程边界）          AOI Cell（8m，进程内视野计算）
┌────┬────┬────┬────┐            ┌─┬─┬─┐
│    │    │    │    │            │ │ │ │  ← 玩家为中心的 3×3
├────┼────┼────┼────┤     →      ├─┼─┼─┤
│    │ ●  │    │    │            │ │●│ │
├────┼────┼────┼────┤            ├─┼─┼─┤
│    │    │    │    │            │ │ │ │
└────┴────┴────┴────┘            └─┴─┴─┘
```

- **Chunk** 决定哪个 Scene 管，是迁移单位
- **AOI Cell** 决定谁能看见谁，是广播单位

九宫格方案：每次移动只需要比较新旧 3×3 区域的差集，复杂度 O(格子内实体数)，与全图规模无关。

视野事件三类，统一在帧末批量处理：

```go
type AOIEvent struct {
    Kind   EventKind // Enter / Leave / Move
    Watcher EntityID
    Target  EntityID
    Pos     Vector3
}

// 关键优化：同一 tick 内同一目标的多次 Move 合并成一次
// 玩家跑动时每帧位置都变，但只需要发送最新位置
```

**降频策略**：逻辑 20Hz，AOI 广播 10Hz，远处的实体再降到 2Hz。这一条能省掉 40% 以上带宽。

### 4.5 移动与寻路 `internal/nav` `internal/game/movement`

| 模块 | 职责 |
|---|---|
| Movement | 速度积分、加速度、地形高度采样 |
| Validator | 服务端校验：单帧位移 ≤ maxSpeed × dt × 容差 |
| PathFinder | A* + NavMesh，异步计算不阻塞 tick |
| Collision | 静态碰撞体（地形/建筑）+ 动态（其他实体） |

防作弊的核心是**服务端权威**：客户端只上报"我想往哪走"，位置由服务端算。客户端做预测只为手感，服务端永远以自己为准，发现偏移就强制校正。

### 4.6 玩法层 `internal/game`

按功能域拆子包，每个子包注册自己的 System 到 Scene：

```
game/
├── creature/    ✅ 参考实现：属性、回血、游荡 AI、属性同步（M2.4 的验收样本）
├── combat/      ✅ 战斗管线：技能、伤害结算、Buff（M4）
├── player/      ⬜ 角色、成长、背包
├── skill/       ⬜ 技能释放、CD、目标选择（M4 已并入 combat）
├── buff/        ⬜ 状态机、持续时间、叠加规则（M4 已并入 combat）
├── quest/       任务状态机、条件判定
├── social/      好友、组队、公会、聊天
├── economy/     交易、拍卖、货币
└── worldevent/  天气、昼夜、刷怪、资源点
```

`internal/game/creature` 是这套约定的最小闭环，写新玩法时照它抄：

```go
var CAttr = ecs.Define[Attributes]("creature.attr")   // 1. 定义组件
func Register(s *world.Scene) error {                 // 2. 注册 System
    s.AddSystemFunc("creature.regen", world.StageLogic, st.regen)
    s.OnEntityEnter(func(ctx *world.Ctx, e *world.Entity) { /* 3. 挂初始组件 */ })
}
```

它只依赖 `world` 和 `ecs`，`world` 完全不知道"怪物"的存在——`cmd/server/main.go` 里一行 `creature.Register(scene)` 就把它挂上了。加一个玩法不改 Scene 一行代码，这就是 M2.4 的验收标准。

**伤害管线**是战斗的核心抽象，固定顺序执行，每步可插拔：

```
原始伤害 → 暴击判定 → 增伤修正 → 减伤修正 → 护盾吸收 → 扣血 → 触发效果
```

写成 pipeline 而不是一堆 if，是为了让策划能配、让程序能加。新加一个"元素抗性"只需要插一个 stage。

### 4.7 AI 与刷怪 `internal/ai`

| 模块 | 职责 |
|---|---|
| BehaviorTree | 行为树，节点可热加载配置 |
| Population | 刷怪管理器：区域配额、刷新冷却、密度上限 |
| Aggro | 仇恨列表、目标选择 |
| GroupAI | 群体行为：编队、集火、包抄 |

刷怪不要用"每只怪一个定时器"，用 Population 在 tick 里统一扫描，按区域配额批量生成。

### 4.8 持久化 `internal/persist`

| 模块 | 职责 | 要点 |
|---|---|---|
| Repository | 存档读写 | 玩家维度分片 |
| DirtyTracker | 脏标记 | 只写变化的字段 |
| Flusher | 定时批量落盘 | 5 分钟全量 + 下线强制 |
| TxLog | 关键操作日志 | 交易、掉落必须可追溯 |

三层存储：

```
内存（运行时权威） → Redis（在线缓存、跨进程共享、宕机热恢复） → MySQL（最终档案）
```

落盘策略要防止"下线瞬间打满数据库"：玩家下线时先写 Redis，再由后台协程异步刷 MySQL。

### 4.9 配置 `internal/config` `tools/excel`

策划用 Excel，程序用二进制。

```
Excel → exceltool → .bin (gob/flatbuffers) → 启动加载到只读 map
```

**热更**：用 atomic.Value 整体替换配置对象指针，正在执行的 tick 继续用旧版本，下一个 tick 用新版本。不要逐条加锁更新。

### 4.10 事件与消息 `internal/eventbus`

两种总线，不要混用：

- **进程内事件**（同步/异步 goroutine）：`player.levelup` → 任务系统、成就系统订阅
- **跨进程消息**（NATS / Kafka）：全服公告、跨服活动、排行榜

进程内事件用发布订阅解耦玩法模块，避免 player 包直接 import quest 包造成的循环依赖。

### 4.11 可观测性 `internal/observability`

| 指标 | 说明 |
|---|---|
| tick_duration | 单帧耗时，P99 超过 50ms 就要告警 |
| scene_entity_count | 场景实体数，判断是否需要拆分 |
| aoi_event_rate | 视野事件速率 |
| packet_loss / rtt | 网络质量 |
| goroutine_count | 泄漏检测 |

链路追踪：一个玩家操作从 Gate 进来，带上 traceID，一路传到 World，能串联出完整调用链。

## 五、控制平面与服务管理

数据面（Gate/World/Data）负责跑游戏，**控制面负责管数据面**。这一块必须独立部署、独立存活——业务进程全挂了，控制台还得能显示"全挂了"并且把它们拉起来。

### 5.1 管理对象是两层

```
区服 Server  (S1、S2、S3……)
  └── 角色 Role  (gate / world / login / data)
        └── 实例 Instance  (gate-s1-001、world-s1-002……)
```

- **区服**是运营单位：开一个区、关一个区、合区
- **实例**是运维单位：某台机器上的某个进程
- UI 上默认按区服聚合展示，点进去看实例明细

### 5.2 实例状态机

七个状态，一一对应看板上的状态灯：

| 状态 | 含义 | 灯色 |
|---|---|---|
| `Pending` | 待调度，进程未拉起 | 灰 |
| `Starting` | 启动中，加载配置、注册 etcd | 黄 |
| `Running` | 运行中，对外服务 | 绿 |
| `Draining` | 排水停服，拒新连接、内存存档 | 黄闪 |
| `Maintenance` | 维护中，进程在但不接新玩家 | 蓝 |
| `Stopped` | 已停止，进程已退出 | 灰 |
| `Failed` | 异常，心跳丢失或启动失败 | 红 |

`Failed` 不是终态，人工可以点重启回到 `Starting`。

### 5.3 开服与关服不是"起进程"和"杀进程"

**开服要按依赖顺序编排**：

```
login → data → world → gate
```

顺序反了会出问题：Gate 先起来，玩家连进来却找不到 World；World 先起来，连不上 Data 会启动失败。用 Saga 模式编排，任一步失败自动回滚已启动的实例。

**关服要走优雅流程**，四步，UI 上做成进度条：

1. **摘流** — 从 etcd 摘除实例，Gate 停止分配新连接
2. **通知** — 给在线玩家推「服务器将在 N 秒后关闭」，N 可配（默认 300 秒）
3. **排水** — 拒绝新请求，等待当前 tick 结束，强制全量存档
4. **退出** — 进程优雅关闭，未落盘数据先写 Redis

超过排水超时（比如 600 秒）还没完成，允许升级为强制停止，但要在审计日志里标红。

### 5.4 控制面架构

```
  管理控制台 (Vue3 + Vite)
        │  WebSocket  ← 状态推送（1s）
        │  HTTP       → 操作指令
  ┌─────▼──────────────────┐
  │  Control API (Go)      │  状态聚合 · 编排 · 审计 · 权限
  └─────┬──────────────────┘
        │  watch / lease
  ┌─────▼──────┐
  │   etcd     │  实例注册 · 心跳 · 配置下发
  └─────┬──────┘
        │
  ┌─────▼──────────────────────────┐
  │  gate / world / login 进程      │
  └────────────────────────────────┘
```

状态采集三条路，以 etcd lease 为准：

| 来源 | 用途 | 频率 |
|---|---|---|
| etcd lease 续约 | 判定存活（主依据） | 5s |
| `GET /healthz` `GET /readyz` | 探测细节（就绪 / 未就绪） | 10s |
| `GET /metrics` | 拉指标填图表 | 15s |

**为什么以 lease 为准**：进程被 OOM kill 时来不及上报任何东西，lease 到期是最可靠的失败信号。HTTP 探活可能因为网络分区误判，只能作为辅助。

**当前实现（M2.3）**：`internal/control` + `cmd/control`，单机版，不依赖 etcd。

| 能力 | 做法 |
|---|---|
| 实例管理 | 控制面直接 `exec` 子进程并持有句柄，能拿到真实退出码 |
| 存活判定 | HTTP 探针（2s）+ 进程退出回调，双信号；回调能区分"崩溃"和"正常停" |
| 编排 | 按区服串行，开服失败按 Saga 逆序回滚已启动实例 |
| 状态持久化 | `logs/control-state.json`，临时文件 + rename 原子写 |
| 控制面重启 | 读状态文件 + 探针，接管还活着的实例（控制面是单点，它重启不该等于全区停服） |
| 控制台 | 单文件内嵌 HTML，1.5s 轮询 `/api/overview`，没有前端构建步骤 |

etcd 版本留到 M3 多机部署时替换 `Registry` 的实现，编排器和 HTTP 层不受影响。

有一个坑值得记下来：状态文件用 `json.Unmarshal` 读，而 Windows 上的编辑器和 `Set-Content -Encoding utf8` 都会在文件头写 UTF-8 BOM，`encoding/json` 遇到 BOM 直接报 `invalid character 'ï'`。不处理的话现象是"重启后所有实例变成未启动"，而且不报错、只留一行警告——这类问题偏偏出现在"人手工改过配置"的时刻。现在加载前会剥掉 BOM。

### 5.5 每个业务进程必须实现的接口

```go
GET  /healthz        存活探针，永远快速返回 200
GET  /readyz         就绪探针，配置加载完 + etcd 注册成功才 200
GET  /metrics        Prometheus 指标
GET  /admin/state    JSON 状态摘要（tick 耗时、实体数、在线数、goroutine 数）
POST /admin/drain    触发排水（进入 Draining）
POST /admin/reload   热加载配置
```

`/admin/*` 走独立端口 + 内网 + token 鉴权，绝不能暴露在公网。

### 5.6 三个可视化视图

**① 区服总览** — 每区一张卡片：状态灯、在线人数、实例数（Running/Total）、CPU/内存水位、今日开服次数。异常区服置顶并标红。

**② 实例列表** — 按 Role 分组，每行显示实例 ID、所在机器、状态、启动时长、版本号。操作列提供启动/停止/重启，危险操作二次确认。

**③ 世界拓扑** — 这张是开放世界特有的：把世界地图的 Chunk 网格画出来，每个格子按当前所属 World 进程上色，颜色深浅表示负载（实体数）。运维一眼能看出哪个 World 快撑爆了，需要拆分区。

配套还要有：

- **操作审计**：谁、什么时候、对哪个实例做了什么、结果如何，不可删除
- **权限分级**：只读 / 运维 / 管理员，关服操作要求管理员
- **操作锁**：同一区服同时只能有一个编排任务在跑，避免两个运维互相打架

### 5.7 控制面 API（已实现）

```
GET    /                               内置控制台（单文件 HTML）
GET    /api/healthz                    控制面自身存活
GET    /api/overview                   区服 + 实例 + 最近任务，一次请求画完整页
GET    /api/tasks                      任务列表（最近 50 条）
GET    /api/tasks/{id}                 单任务进度（含逐步 step）
POST   /api/zones/{id}/start           开服（异步，202 + taskId）
POST   /api/zones/{id}/stop?grace=10   优雅关服，grace 秒倒计时
POST   /api/instances/{id}/start       单实例启动（排障用）
POST   /api/instances/{id}/stop        单实例停止
```

`/api/overview` 把区服、实例、任务放在同一个响应里，让前端一次请求画完整个页面，避免"区服卡片已经更新、实例列表还是上一秒"的割裂感。

**幂等**：同一个区服同一个操作在进行中时，再次调用返回同一个 taskId，不会起第二个任务。前端连点两下不会变成两个协程抢同一个端口。

开服/关服都是**异步任务**，接口立刻返回 taskId，前端轮询进度。不要做成同步阻塞接口——一次关服要等玩家 300 秒倒计时。

## 六、关键机制详解

### 6.1 Tick 分层

不同系统不需要同一频率，硬绑在一起是浪费：

| 频率 | 系统 |
|---|---|
| 20Hz (50ms) | 移动积分、AI、Buff 计时 |
| 10Hz (100ms) | AOI 广播、战斗结算 |
| 1Hz | 属性重算、任务条件检查 |
| 事件驱动 | 技能释放、交易、聊天 |

实现上是一个 `Scheduler`，每个系统注册自己的间隔，主循环按帧号取模触发。

### 6.2 跨 Chunk 迁移（Handover）

实体从 Scene A 走到 Scene B，必须在线完成，流程如下：

```
1. A 在 tick 中发现实体位置超出 Chunk 边界
2. A 给 B 发 HandoverPrepare{entityID, snapshot}，同时冻结该实体（不接受新指令）
3. B 收到后创建实体副本，挂到自己的实体表，回 HandoverReady
4. A 收到 Ready，删除本地实体，更新 Redis 归属表，回 HandoverCommit
5. B 收到 Commit，解冻实体，重算 AOI，给客户端推新的视野列表
6. 任一步超时（比如 3 秒）→ A 回滚，实体留在原地并重新激活
```

关键点：
- **冻结期**必须有超时，否则一次网络抖动会永久卡住实体
- **归属表更新放在第 4 步**，保证任何时刻查询都不会指向两个 Scene
- 客户端在切换期间感知不到，只是收到一批 Enter/Leave 事件

### 6.3 视野同步的带宽控制

一个 100 人同屏的场景，如果每人每帧都广播位置，就是 100×100×20 = 20 万条消息/秒。必须做三件事：

1. **只同步视野内**：AOI 把 100×100 降到 100×20（视野半径内约 20 人）
2. **合并同帧多次更新**：跑动时只发最新位置，不发中间过程
3. **降频 + 插值**：远处实体 2Hz 更新，客户端做位置插值

### 6.4 空间索引与单场景容量（M2 实测）

**实现**：`internal/aoi`，泛型 `Grid[T]`，三条设计原则。

1. **格子内用 slice 而不是 map**。同格实体在内存里连续，遍历快 3~5 倍；删除用 swap-remove + 索引表保持 O(1)。
2. **格子尺寸和视野范围解耦**。格子多大是存储问题，视野多大是玩法问题，绑死会导致"想改视野就得重建索引"。配置入口是 `WithAOI(cellSize, radius)`。
3. **差集查询不构造临时集合**。跨格时新旧视野重叠 90% 以上，遍历新视野 + `InView` 判旧视野即可求差，省掉每次跨格的两次 map 分配。

**M2.3 之后，容量约束换了一套**

移动改走意图缓冲（见 6.5）之后，它不再占用邮箱，也不再受单帧消息配额约束。现在只剩两条：

| 约束 | 位置 | 说明 |
|---|---|---|
| 广播成本 ∝ 邻域人数 | `Grid.ForEachNear` | 唯一随人数增长的开销，决定密度上限 |
| 心跳超时扫描 O(N) | `Scene.reapIdle` | 每帧遍历全部实体，2 万人约 0.2ms/帧 |

`maxCmdsPerTick=4096` 现在只约束控制指令（进入/离开/心跳）。1 万人、心跳 1Hz 时每帧约 500 条，余量 8 倍——这条配额已经不再是天花板，保留它只是为了防"一批玩家同时上线"把某一帧撑爆。

性能上限完全由密度决定（`go test ./internal/world -bench BenchmarkMoveBroadcast`，i5-7500 单核，16m 格 / 48m 视野）：

| 分布 | 每格人数 | 单条位移（含广播） | 半帧预算（25ms）可支撑 | M1 旧实现 | 提升 |
|---|---|---|---|---|---|
| 2000 人散落 1000m | ~0.5 | ≈460 ns | 约 5.5 万 | 1.42 µs | 3.1× |
| 2000 人集中 300m | ~5.6 | ≈1.4 µs | 约 1.8 万 | 5.31 µs | 3.8× |
| 2000 人挤 100m 主城 | ~51 | ≈5.5 µs | 约 4500 | 54.2 µs | 9.9× |
| 5000 人散落 1000m | ~1.0 | ≈740 ns | 约 3.4 万 | 2.58 µs | 3.5× |

口径说明：一帧 50ms，只把一半预算（25ms）留给位移结算，另一半留给玩法、AI 和广播抖动。因为每个实体每帧最多结算一次位移，"每帧能结算多少条"直接等于"这个密度下能装多少实体"。

主城密度的提升（9.9×）必须拆成两个独立因素，否则会高估代码的价值：

- **纯实现优化**：同样 32m 格 / 96m 视野，旧实现 54.2 µs → 新 15.9 µs，**3.4×**，来自 slice 连续遍历和零分配求差集。
- **视野缩小**：96m → 48m 见方，15.9 µs → 5.5 µs，**2.9×**，来自邻域人数减到 1/4。

第二项不是优化而是取舍——96m 视野对开放世界过大，客户端渲染 96m 外的角色也很浪费。48m 是主流 MMO 的取值。**视野是最大的性能杠杆，也是最需要玩法侧确认的参数。**

测试环境说明：这台机器是 4 核开发机，同机压测时 bot 和 server 抢同一批核，数字有 ±20% 的抖动。上表的量级可信，小数点后一位不可信。

### 6.5 移动输入：写后合并（M2.3 实测）

**问题**：M2 做完 AOI 后，主城容量从 590 提到 7000 多，但 `maxMsgsPerTick=4096` 变成了先到的那道墙——8192 实体 × 10Hz 移动正好把每帧配额打满。继续加配额只是把墙往后推。

**根因是"把移动当消息"**。移动不是事件，是状态：客户端发的是"我现在在哪"，不是"我走过了哪几步"。给状态用队列，就必然会重复处理同一个实体的多个版本。

**改法**：移动不再进 mailbox，改为按 entityID 分 16 片写入意图缓冲（`internal/world/intent.go`），tick 时统一结算，每个实体每帧只结算最后一次。

```go
// 写入方：每个连接的读协程
func (s *Scene) Move(id uint64, x, y, z float32) {
    sh := &s.intents[id%intentShardCount]
    sh.mu.Lock()
    sh.m[id] = moveIntent{x, y, z}   // 后写覆盖先写，没有队列
    sh.mu.Unlock()
}

// 读取方：tick 协程。先拷出来、clear、放锁，再结算
s.moveScratch = s.intents.drainTo(s.moveScratch[:0])
for _, mv := range s.moveScratch { s.applyMove(mv.id, mv.x, mv.y, mv.z, now) }
```

三个关键点，每个都对应一次踩坑：

1. **每帧工作量有了上界**。N 个实体，一帧最多 N 次位移结算，与客户端发包频率无关。作弊客户端每秒发 1000 次移动，服务端成本和一个正常客户端完全一样。
2. **必须先拷出来再放锁**。结算会触发广播，`Send` 可能阻塞在写队列上；持锁结算会把所有上行读协程一起拖住。
3. **用 `clear` 而不是重新 `make`**。Go 的 `clear` 只清空 bucket、保留已分配的桶数组，稳态零分配；重新 make 会让每帧固定产生 16 次 map 分配。

另外一个副作用收益：`post(&msgMove{...})` 原来每条消息一次堆分配，现在完全没有。

**实测**（400 机器人，40Hz 发包，是 tick 频率的 2 倍）：

| 指标 | 数值 |
|---|---|
| 接收一条意图 | 46.5 ns，0 allocs |
| 合并率 | 51.4% |
| tick 滞后 | 0.13 ms |
| `mailboxDropped` | 0（移动路径不再可能丢包） |

合并率是新增的观测指标（`moveIntents` / `moveApplied` 之比）。两个用途：判断客户端是否发得比 tick 快（合并率高说明可以降频省电），以及暴露异常客户端（合并率接近 100% 说明在刷包）。

**这条经验可以推广**：所有"高频、只关心最新值"的输入（朝向、按键状态、相机方向）都应该用覆盖式缓冲，而不是消息队列。判断标准只有一句——丢掉中间值会不会影响结果？会，就用队列；不会，就用缓冲。

### 6.6 ECS：组件存储与 System 管线（M2.4 实测）

**问题**：M2 的实体是一个固定结构体（`id/x/y/z/speed/client`）。加战斗就要往里塞 HP、攻击、防御，加 AI 就要塞状态机、目标、冷却。两个后果：

1. 每个玩家都为"怪物才有的字段"付内存，10 万实体就是几十 MB 的纯浪费；
2. `world` 包被迫知道所有玩法概念，`game` 和 `world` 纠缠在一起，没法独立演进。

**改法**：`internal/ecs` 提供按类型连续存储的组件池，`Entity` 只留"高频且所有实体都有"的字段（位置、速度、所在格）。玩法数据全部进组件，玩法逻辑以 System 形式挂在四个阶段上。

#### 为什么是稀疏集，不是 archetype

| | 稀疏集（本项目） | archetype（flecs / bevy） |
|---|---|---|
| 增删组件 | O(1)，一次数组交换 | O(组合大小)，实体要在表之间搬家 |
| 增删后指针 | dense 内指针失效，外部指针不受影响 | 整行搬家，所有引用失效 |
| 按组合批量遍历 | 从最小池出发查其他池 | 直接顺序扫表，最快 |
| 内存 | 每池 4B × maxID 的稀疏数组 | 按组合分表，碎片少但迁移有峰值 |

选稀疏集的理由不是"更先进"，是**开放世界的负载形状**：玩家进出、怪物刷新、掉落物生成，增删频率远高于"同一组合的大批量遍历"。archetype 的优势场景（几千个同构实体每帧全量跑同一个系统）在副本和战场里才成立，主城不是。

#### 泛型池，不用反射也不用 `[]any`

```go
type Attributes struct{ HP, MaxHP int32; Level uint8 }
var CAttr = ecs.Define[Attributes]("creature.attr")

pool := ecs.Get(scene.Store(), CAttr)   // *ecs.Pool[Attributes]
pool.Add(id, Attributes{HP: 100})
pool.Each(func(id uint64, a *Attributes) { a.HP++ })
```

`Pool[T]` 内部是三个切片：`sparse []int32`（实体 ID → dense 下标+1）、`dense []T`、`ids []uint64`。删除用 swap-remove（把最后一个搬到被删位置），O(1)、无空洞，代价是 dense 顺序不稳定。

泛型相比 `[]any` 的收益是实测的，不是估的：

| 1 万个组件的整表只读遍历 | 耗时 |
|---|---|
| `Pool[T].Each`（连续 `[]T`） | 15.8 µs |
| `[]any` + 类型断言 | 29.1 µs |

差距只有 1.8 倍，因为遍历的回调调用本身盖住了一部分。**真正拉开差距的是写入**：往 `[]any` 里写每次都要装箱分配，往 `[]T` 里写是一次内存赋值。所以判断标准是"这块数据是读多还是写多"，属性/Buff 明显是写多。

> 第一次写这个基准时测出 `[]any` 慢 40 倍，其中 39 倍是每轮 1 万次装箱分配，不是内存布局的锅。基准写错方向，比不写更危险。

#### 四个阶段，语义写死

```go
scene.AddSystem(&world.System{Name: "combat", Stage: world.StageLogic, Tick: combat.Tick})
```

| 阶段 | 谁在里面 | 为什么放这儿 |
|---|---|---|
| `StageCommand` | 属性初始化、进场补数据 | 要在"实体刚落地"时生效，且能被本帧 AI 看到 |
| `StageInput` | 内置 `world.move`（位移结算） | 本帧输入到此为止，之后的位置是稳定值 |
| `StageLogic` | AI、战斗、Buff、任务 | 写的位移意图**下一帧**结算，不允许同帧回写 |
| `StageReplicate` | 属性同步、统计快照 | 只发消息不改状态，看到的永远是本帧最终结果 |

"AI 的决策下一帧才生效"是刻意的：如果同帧结算，System 的注册顺序就会影响结果，回放和压测都不可复现。代价是最多 50 ms 的输入延迟，玩家感知不到。

**panic 隔离**：每个 System 单独 `recover`，一个系统炸了不影响同帧其他系统；连续 3 次 panic 后自动停用并打 error 日志。没有这层，某个玩法一个越界就会让整帧后续逻辑全部跳过——表现是"某个功能坏了之后，全服玩家都不动了"。

#### 属性下发靠脏标记，不靠轮询

`Attributes.Dirty` 在组件里，改属性时顺手置位，同步系统遍历时清掉。

实测（2000 只怪，出生 60% 血，每秒回 2%）：

| 时间 | 属性包速率 |
|---|---|
| 前 5 秒（怪在回血） | 约 11k 包/秒 |
| 20 秒后（全部满血） | **0** |

满血之后整条链路彻底静默。这比"每帧全量广播属性"省的不是百分比，是几个数量级——如果按 20Hz 广播，2000 只怪 × 20 × 视野内 16 人 = 640k 包/秒，光这一项就能把一台机器吃满。

#### 实测：ECS 到底花掉多少帧预算

单帧 CPU（2000/5000 只怪，i5-7500 单核，`-benchtime=100ms`）：

| 场景 | 单帧耗时 | 说明 |
|---|---|---|
| 2000 怪 · 不挂系统 | 30 µs | 只有心跳扫描和统计 |
| 2000 怪 · 挂 AI + 回血 + 属性同步 | 88 µs | 0.18% 的 50ms 帧预算 |
| 5000 怪 · 挂 AI | 252 µs | 0.5% |
| 3000 怪 · 单跑 wander 全表扫描 | 85 µs | 约 28 ns/只，含移动与广播 |
| 3000 怪 · 单跑 regen 全表 | 3.2 µs | 约 1 ns/只 |
| 3000 怪 · 属性脏检查 | 8.2 µs | 约 2.7 ns/只 |
| 组件挂载 + 卸载（2 个组件） | 33 ns | 实体进出场的固定成本 |

结论：**ECS 本身几乎不花钱，钱花在它引发的事上**——每只怪每帧移动一次，就要给视野内每个玩家发一个包。怪物的成本和怪物的数量不是线性关系，是"怪物数 × 视野内玩家数"。

#### 端到端：广播只发给玩家

第一版把广播发给视野内所有实体，NPC 的出口是空实现（`nopClient`）。2000 只怪挤在 300 米半径里时，一半以上的收件人是另一只怪——纯浪费。

改成只发给 `KindPlayer` 之后：

| 1000 玩家 + 2000 怪 | 广播量 |
|---|---|
| 修前 | 约 550k 包/秒 |
| 修后 | 约 79k 包/秒 |

代价是热循环里多一个 `o.kind != KindPlayer` 分支（可预测，几乎免费），收益是 85% 的广播消失。

端到端 RTT（本机 4 核，服务端与 1000 个机器人同机竞争 CPU）：

| 场景 | avgRTT | 结果 |
|---|---|---|
| 1000 玩家 + 0 怪 | 38 ms | 0 失败、0 丢弃 |
| 1000 玩家 + 2000 怪 | 66 ms | 0 失败、0 丢弃、0 panic |
| 500 玩家 + 2000 怪 | 21 ms | 1.04M 状态包 / 20 秒 |
| 0 玩家 + 2000 怪 | — | 服务端 CPU 占用约 0% |

最后一行是关键：**没有玩家在视野里时，2000 只怪的 AI、位移、索引维护几乎不耗 CPU**。怪物是"广播放大器"，不是"计算放大器"。

#### 三个坑

1. **稀疏数组按 maxID 增长**。每个池一份 `[]int32`，内存 = 4B × 历史最大 ID × 池数量。实体 ID 单调递增且不复用，长跑之后会一直涨。这就是 6.7 节要解决的问题。
2. **遍历中增删同一个池会踩到 swap-remove**。`Each` 的循环变量是 dense 下标，删除会把末尾元素搬到当前位置——如果末尾还没遍历到，它就被跳过了。要边遍历边删，先 `IDs()` 取快照。
3. **`Store.Stats()` 只能在 tick 协程里调**。它读的是 `len(dense)`（切片头），跨 goroutine 读就是数据竞争。对外暴露的是每秒一次的不可变快照（`atomic.Pointer[[]PoolStat]`），HTTP 线程只读快照。

### 6.7 实体 ID 回收（M3.1 实测）

**问题**：稀疏集用实体 ID 直接下标寻址，所以 `sparse` 的长度等于"历史最大 ID"。ID 单调递增不复用的话，一个场景跑一天、玩家进出几十万次之后，每个组件池都摊着一个几 MB、全是 0 的数组，而场景里同时只有几千人。这部分内存不是逻辑需要，纯粹是 ID 空间漏了。

**为什么不能直接复用**：客户端在途的包里带的是旧 ID（Move / Heartbeat / Leave）。ID 一被复用，这些包就打到了新实体身上——表现是新怪刷出来就"自己走了一步"，或者新玩家进场时血量是上一个人的。这类 bug 在压测里几乎抓不到，只有线上偶发。

#### 三段式 ID 空间

```
       ┌─────────── live：已分配未释放 ───────────┐
  1 ───┼──────────────────────────────────────────┼─── next
       └──────────────────────────────────────────┘
                                    free（可复用，LIFO 栈）
                                    cool（冷却中，按释放时间有序）
```

- **分配**：先弹 `free`，空了才推高 `next`。这是整个机制生效的关键——只要还从 `free` 里拿，高水位就不会动。
- **释放**：进 `cool`，记下释放时刻。
- **复活**：分配时顺手把冷却期（2 秒）已满的前缀挪进 `free`。

#### 四个设计决定

| 决定 | 理由 |
|---|---|
| 冷却 2 秒，按时间不按 tick | 按 tick 计数的话，改了 `-tick-ms` 就等于改了安全性；而且 20Hz 和 200Hz 的"40 帧"完全不是一回事。用时间才和 tick 率解耦。2 秒 = 公网 RTT 的 5~10 倍余量 |
| `free` 用 LIFO 栈 | 刚回收的 ID 最近被用过，稀疏数组对应的那几行还在 cache 里 |
| 上限 1<<20，耗尽返回 0 | 1M × 4B = 4MB/池，是能接受的兜底。碰到上限说明有泄漏，此时**拒绝新实体**在监控上是一个刺眼的计数器，比几小时后一次 OOM 好 |
| 加一把 mutex | 分配发生在两个 goroutine：玩家进场走 Gate 读协程（要同步拿 ID 填会话），NPC 生成在 tick 协程。搬进 tick 可以让它无锁，但进场就要等一帧（50ms），且会阻塞 Gate 读协程 |

#### 实测

单测（`TestSparseArrayGrowth`，同一段代码只改冷却策略，累计 2 万次生灭、峰值 2000）：

| 实验臂 | ID 高水位 | sparse 长度 | 每池寻址内存 |
|---|---|---|---|
| 不回收（冷却 1 小时） | 20000 | 32752 | 127 KB |
| 回收（冷却 2 秒） | 2000 | 2032 | 7 KB |

**16 倍**，而且差距是线性的：不回收那一臂的 sparse 直接等于累计实体数，跑多久涨多久。

端到端（2000 只怪常驻，前后 6 轮各 400~500 个机器人登录再断开，共约 2600 次进出）：

| 时刻 | ID 高水位 | 复用次数 | sparse（attr/brain） |
|---|---|---|---|
| 只有 2000 怪 | 2000 | 0 | 2032 / 2032 |
| 3 轮之后 | 2497 | 880 | 4080 / 2032 |
| 6 轮之后 | **2497** | 2169 | 4080 / 2032 |

第 6 轮和第 3 轮的高水位一模一样——**再多的进出也不再推高水位了**。不回收的话 6 轮之后应该是 2000 + 2600 = 4600。

分配开销（`BenchmarkIDAlloc`）：新号 37 ns、复用 64 ns、都是 0 分配。复用比新号慢，是因为要多走一次冷却队列前缀扫描；一天几万次进出的量级下，这点差别可以忽略。

#### 踩到的三个坑

1. **`cool = cool[head:]` + `append` 会退化成每次分配一次堆分配**。切片前移不回收容量，`cap` 一路缩到 0，之后每次 append 都要重新分配——实测复用路径变成 295 ns/op、32 B/op，比分配新号还慢 8 倍。改成"游标 + 定期原地压缩"后是 64 ns、0 分配。
2. **游标只进不退，冷却队列自己会漏**。修完第 1 条之后 `cool` 数组的头部是死空间，只要没有"冷却队列被清空"的空闲时刻，长度会跟着累计释放次数涨——等于把"ID 空间泄漏"换成了"队列泄漏"。所以加了摊还压缩：死空间占到一半就整体前移（`TestIDCoolQueueBounded` 守着这条）。
3. **邮箱满时已经分出去的 ID 没还回去**。`Enter` 是先分配 ID、再投递 `msgEnter`；邮箱满时投递失败，实体永远不会真的建出来，那个 ID 就永久漏了——而且泄漏量正比于登录洪峰。现在投递失败会立刻 `release`，并返回 0 让 Gate 回一个"场景已满"。

### 6.8 多场景与跨场景迁移（M3.2 实测）

**问题**：一个 Scene 一个 goroutine，单场景容量就是单核容量（实测约 7000 人在 48m 视野下）。开放世界不可能只有一张图，必须有"按地理切分、各自跑各的"的能力。

#### 两级分区，各管一件事

| | Chunk（512m） | AOI Cell（16m） |
|---|---|---|
| 回答什么 | 这块地归谁管 | 谁能看见谁 |
| 变更成本 | 一次数据迁移 | 重建索引 |
| 所以它 | 粗、稳定、按拓扑分配 | 细、可调、每场景独立 |

两者解耦是刻意的：调视野半径是玩法迭代，一天可能改十次；改 Chunk 边界是一次线上迁移，一个月不该超过一次。绑在一起会让"想调视野"变成"想动拓扑"。

#### 边界必须按 Chunk 对齐

`Topology.Add` 会拒绝不对齐的矩形。原因不是洁癖：

Chunk 是归属的最小单位，如果场景 A 是 `[0,300)`、场景 B 是 `[300,600)`，那么 Chunk 0 覆盖 `[0,512)`，横跨两个场景。`Route(x)` 只能把 Chunk 0 判给其中一个，于是：

- 判给 A，那么 B 的玩家在 x=350 时按 Chunk 路由会回到 A，A 又不包含 350 → 每帧发起一次迁移 → 玩家在边界上原地抖动；
- 判给 B，那么 A 的玩家在 x=100 时被路由到 B，同样抖。

对齐之后 `Route` 的结果必然被目标场景包含，这个死循环从根上不存在。校验成本是一次除法，收益是消灭一整类"只在边界出现"的诡异现象。

#### ID 空间必须上移到 World

这是 M3.2 最不显然的一个决定。迁移时实体必须**保留原 ID**（客户端靠它认自己的角色），于是目的场景会拿到一个"不是自己发的" ID。如果每个场景各有一份分配器（M3.1 的做法），就必须回答：

> 这个外来 ID 离开目的场景时，该由谁回收？

- 让目的场景回收 → 它可以把这个 ID 再发出去，而原场景还以为它属于自己，两个场景的玩家在同一个客户端眼里撞号；
- 让源场景回收 → 需要一条"归还"消息，这条消息会丢、会重复、会在源场景已经关闭时无处可去。

上移一层，问题消失：**ID 属于世界，不属于场景**。代价是所有场景的稀疏数组都按全局高水位分配，一个 3000 人的世界在 1000 个场景里会有 1000 份 12KB 的数组——12MB，可接受；换来的是零协议、零泄漏路径。

#### 三阶段握手

```
A: 玩家走到 x > 512（A 的边界）
   │
   ├─ Prepare ──▶ B   问：这个人能过来吗？（B 校验容量、是否在排水）
   │  ◀── Ack ───     能 / 不能（满了 / 在关服）
   │
   ├─ Ready            A 摘除实体，给旧视野发 Leave，给玩家本人发旧视野的 Leave
   │
   └─ Commit ──▶ B    A 把实体状态发过去，B 落地、给新视野发 Enter、通知会话切场景
```

**为什么必须先问再摘**：如果 A 先摘了、B 才说"满了"，A 就得把自己刚删掉的人再塞回去——位置、组件、视野全要重建，而这期间玩家是"消失"的。先问一句的成本是一条消息，换掉一整类回滚。

**为什么 Commit 还要运数据**：Prepare 阶段两边只有 token，没有实体内容。这样即使 Prepare 被拒、超时、或者源场景崩溃，目的场景也没有任何状态需要清理。

#### 三条失败路径，都要有明确归宿

| 失败 | 表现 | 处理 |
|---|---|---|
| B 拒绝（满了 / 排水） | Ack 回 false | 实体留在 A，位置夹回边界内，`handoverFails++` |
| B 不回（卡死 / 消息丢） | 3 秒超时 | 同上。3 秒是"对方一个 tick 就该回复"的 60 倍余量 |
| Commit 投递失败 | B 的邮箱满了 | 实体已从 A 摘除，用 payload 原地重建回 A。这是唯一一条"两边都没有"的路径，单独处理 |

第三条路径看起来不可能（邮箱 8192，Prepare 刚通过），但它是唯一会让玩家永久消失的分支，所以宁可多写 20 行也不留一个"理论上不会发生"。

#### 实测

3 个场景（1×3，每个 512m 见方，边界 0 / 512 / 1024 / 1536）× 200 只怪，300 个机器人在 x∈[40,1500] 来回走，反复穿越 512 和 1024 两条边界：

| 指标 | 数值 |
|---|---|
| 机器人登录成功 | 300 / 300，失败 0，丢弃 0 |
| 迁移次数（服务端迁出 / 迁入） | 105 / 105，**完全配平** |
| 迁移失败 / 超时 | 0 / 0 |
| 客户端侧观测到的场景切换 | 105（与迁出数一一对应） |
| 结束后各场景实体数 | 200 / 200 / 200，总量守恒 |
| 位移包总数 / 被超速钳制 | 512,536 / 15（0.003%） |
| tick 滞后 | 0.13 ms |
| 平均 RTT | 3.9 ms（同机 4 核，bot 与 server 抢核） |

登录分流是按玩家 ID 散列做的，300 个玩家均匀落到三个场景，而不是全挤在默认场景里——拓扑只对"走过去的玩家"生效的话，登录洪峰照样能把首个场景打满。

那 15 次钳制全部出现在刚落地的那一帧，原因见下面第 5 条坑的姊妹现象：摘除实体时意图缓冲里最多一两个包会跟着一起丢掉，落地后第一包的位移要一次补回来，正好越过速度上限。量级上不值得为它加"跨场景搬运意图"的复杂度——下一次状态包会把客户端位置纠正过来。

更早的一次长跑（同样配置，跑满 60 秒但迁移 127 次）里，客户端只观测到 126 次切换，差的那一次是断线恰好落在迁移窗口内，见第 4 条坑。

#### 五个坑

1. **同名指标在多场景之间互相覆盖**。自研指标注册表按名字去重，三个场景注册 `scene_entity_count` 只有第一个生效，注册 `scene_broadcast_total` 则三个场景共用同一个计数器——控制台上三个场景的广播量永远相等，看着像 bug，其实是指标系统在骗人。改成 `name{scene="N"}` 的标签序列后，`HELP`/`TYPE` 每个 family 只输出一次，同一 family 的多条序列挨着输出。
2. **压测工具本身挡住了被测路径**。机器人沿用单场景时代的 `±495` 硬夹取，永远走不到 512 的边界，第一次跨场景压测结果是"0 次迁移"，看起来像服务端没实现。给压测工具加新路径时，要检查它有没有旧假设把新路径堵死——这类"测试通过但测的不是那个东西"比测试失败危险得多。
3. **迁移期间冻结输入会在边界留下一串 `moveRejected`**。最初的做法是"迁移在途就丢弃位移"，理由是"别让落点取决于两个场景的调度顺序"。实测下来玩家在边界处会丢掉约 100ms 的输入，客户端多走半米，落地后第一包的位移刚好卡在速度上限附近被钳制。改成"源场景继续接收位移、Commit 时用实体的当前位置"之后，落点天然就是最新的，也不需要特殊处理。
4. **断线可能恰好落在迁移那一两个 tick 里**。此时 Gate 读到的还是旧场景，`Leave` 投到已经摘除实体的源场景，目的场景会多出一个没有会话的实体。处理：源场景收到找不到实体的 `Leave` 时，如果它正在迁出，就把这条指令转给目的场景；仍然漏掉的，靠心跳超时兜底（落地时 `lastHeartbeat` 会重置，所以最多多活一个超时周期）。实测 127 次迁移里出现 1 次，30 秒后自动清掉，总量回到守恒。
5. **压测工具的行走区间没盖住出生点，刷出一批假的服务端拒绝计数**。第 3 条修完之后 `moveRejected` 还剩 300 多次，而且高度集中在首尾两个场景、中间场景几乎为 0。打开 debug 日志才看清：被拒的只有 7 个机器人，每条都是 `from=1519.10 to=1500.00 dist=19.10` 这种"一步跨 19 米"。出生点是世界按玩家名散列算出来的，落在 `[0,1536)`，而行走区间是 `[40,1500]`；出生在区间外的机器人第一个移动包就把坐标拽到端点，服务端按超速钳制——完全正确，是压测工具在制造瞬移。中间场景出生范围 `[512,1024)` 整个在区间内，所以它是 0。修法是让每个机器人的折返区间扩到包含自己的出生点。修完 337 → 15。

    这个坑的教训不是"记得改压测工具"，而是：**当一个计数器的分布形状明显偏离预期时，先看分布，再看总量**。总量 337 在 50 万次位移里完全可以被当成噪声忽略掉；按场景切开才发现它根本不是噪声，是两种不同成因叠在一起。

复现：

```bash
./bin/server.exe -partition 1x3 -scene-size 512 -mobs 200
./bin/bot.exe -n 300 -duration 60s -move 100ms -walk x -min-x 40 -max-x 1500
# 跑完看 http://127.0.0.1:7002/admin/state 的 handoversOut / handoversIn
```

### 6.9 跨进程迁移（M3.3 实测）

6.8 的所有机制都建立在"两个场景在同一个进程里、可以直接往对方的 mailbox 投消息"之上。M3.3 把这条投递路径换成网络，并回答三个问题：

1. 一块地属于别的进程时，本进程怎么知道该把 Prepare 发给谁？
2. 实体在 B、玩家的 TCP 连接在 A，B 发的包怎么回到玩家？（这是整个 M3.3 最硬的问题）
3. ID 分配器各进程一份，怎么不撞号？

#### 拓扑从"本地对象"变成"全局地址"

`Topology` 的 owner 从 `*Scene` 换成 `mesh.Peer{Node, Scene}`。每个节点加载**同一份**世界配置：

```json
{ "nodes": { "n1": "127.0.0.1:7003", "n2": "127.0.0.1:7103" },
  "scenes": [ { "id": 1, "node": "n1", "rect": [0,0,512,512] },
              { "id": 2, "node": "n2", "rect": [512,0,1024,512] } ] }
```

属于自己的场景建出 `*Scene`，别人的只 `DeclareRemote` 登记边界——本进程对那块地上的实体一无所知，唯一需要知道的是"走到这里该找谁"。不登记别人的地，玩家走到边界就会 `Route` 落空，表现是"贴着边界走不过去"。

#### 连接不跟着实体走，而是让包跟着连接走

TCP 连接不能跨进程搬。玩家走到 n2 的场景时，他的 socket 还接在 n1 的 Gate 上。于是：

```
   n1（连接 + scene 1）                      n2（scene 2）
     Session(conn)                             Scene 2
        │ rt.node=n2                              │
        ├ Move ──relay──▶ ────────────────────▶ Move(entity)
        │                                         │
        │ ◀──ClientSend（每个下行包一帧）─────────┤ 广播/Enter/Leave
        │                                         │
        │ ◀──Rebind（落地后一次）─────────────────┤ Commit
        ▼
   写 socket
```

三件配套的东西：

- **`ClientRef{Node, Session}`**：实体的"连接地址"。迁移时 payload 里带的是它，不是 `Client` 接口值——接口值过不了网络，源进程的 Session 指针在目的进程里也没有意义。
- **`remoteClient`**：落地节点拿到的 `world.Client` 实现。`Send` → 一帧 `MsgClientSend` → 接入节点 → 写 socket。它的 `Locate()` 永远返回最初那个连接，所以玩家搬三次家也不会把包发丢。
- **`Rebind`**：落地后通知接入节点"这个会话的实体现在在 n2 的 scene 2"。接入节点据此把 Move/Heartbeat 从"投本地场景"改成"转发给 n2"，并清掉本地场景指针（否则会继续往一个已经不属于它的实体 ID 写位移）。

**为什么不做"每个节点都有可能持有连接"**：那需要知道"玩家的连接在谁身上"，等于把 Gate 的位置也做进路由表，而且断线时还得跨节点清理。当前的模型只有一条规则：**连接在哪进来就永远在哪，实体爱去哪去哪**。

#### ID 空间按节点分区

每个进程各有一份 `idAlloc`，各自从 1 开始数就必然撞号——两个不同的人拿同一个 ID，一旦同屏，客户端会把他们认成一个人。

解决办法是**步长分区**：

```
id = seq × stride + offset        stride = 节点数，offset = 本节点在排序后的节点表里的下标
n1(3 个节点里的第 0 个): 3, 6, 9, 12 ...
n2(3 个节点里的第 1 个): 4, 7, 10, 13 ...
n3(3 个节点里的第 2 个): 5, 8, 11, 14 ...
```

不同节点的 ID 落在不同的同余类上，物理上不可能相等。单进程时 `stride=1, offset=0`，分配结果与 M3.2 完全一致。

为什么不用"高 16 位放节点号"（更常见的做法）：组件池用实体 ID **直接下标寻址**，高位编号会让每个池的稀疏数组至少长到 `2^16 × 节点数`。3 个节点就是十几 MB 的空数组。步长分区只把水位放大 `stride` 倍（3 节点、2000 实体约 6000 槽），代价可以忽略。

**配套的一步是必须的**：实体在别的节点死掉时，那个节点不能自己回收（会让本节点发出别人的 ID），只能发 `MsgReleaseID` 通知所有者。不做这一步，M3.1 花力气做的冷却回收就在跨区玩家身上失效，稀疏数组又开始随累计登录上涨。实测一次 60 秒压测里如果跳过通知，n1 会永久多出 100 个"在用"的 ID。

#### 实测

两个进程（n1 持场景 1，n2 持场景 2、3），边界 0 / 512 / 1024 / 1536；每场景 100 只怪；400 个机器人分两批从两个 Gate 接入，沿 X 轴来回穿越：

| 指标 | 数值 |
|---|---|
| 登录成功 | 400 / 400，失败 0 |
| 迁移（迁出 / 迁入） | 149 / 149，**完全配平** |
| 迁移失败 / 超时 | 0 / 0 |
| 客户端观测到的场景切换 | 149，与迁出数一一对应 |
| 结束后各场景实体数 | 100 / 100 / 100，总量守恒 |
| 节点间帧数（n1 发出 / 收到） | 28,739 / 73,518 |
| 队满丢帧 / 发送失败 / 拨号失败 | 0 / 0 / 0 |
| ID 账目 | n1 live=100（仅怪）、cooling=200；n2 foreign=100、live=200 |
| 节点日志告警 | 0 |

ID 那一行值得单独看：n1 有 200 个玩家 ID 全部回到冷却队列（`live` 只剩 100 只怪），n2 记下 100 个"外来 ID"且都已通知 n1 回收。跨进程之后 M3.1 的账仍然是平的。

RTT 从单进程的 3.9ms 升到 14.3ms（n1 侧）/ 26.8ms（n2 侧）。这不是链路开销——同机跑 4 个进程抢 4 核，其中两个是 400 个机器人的压测进程。跨节点玩家的每个下行包多一次进程跳转和一次序列化，但这部分在 4 核满载的情况下被 CPU 抢占放大了。

#### 四个坑

1. **链路队列满时"关连接"，把在途的迁移消息一起丢了**。第一版直接复用客户端的 `Conn.Send`：队列满就断开。压测里出现 8 次 `handover aborted: timeout`，n2 侧 12 次发送失败，而两个节点的日志里没有任何"Admit 收不到"的记录——因为 Prepare 根本没被发出去：它排在队列里，前面 256 帧数据包把队列顶满，连接被关，队列里所有帧一起蒸发。源场景 3 秒后超时回滚，日志上只有一句 timeout。

    修法是给节点链路换成 `TrySend`：**队列满只丢当前这一帧，不断开连接**。丢一帧广播的代价是玩家少看一次别人的位置更新，下一帧就补上；丢一帧 Prepare 的代价是一次失败的迁移。两类消息在同一条链路上，不该共用同一种拥塞策略。

2. **丢了输入帧会让服务端和客户端位置错位**。修完第 1 条后迁移已经 0 失败，但 `moveRejected` 从 15 涨到 855：跨节点玩家的位移帧也走那条链路，拥塞时被丢，下一帧的位移距离变成两倍，超过速度上限被钳制，然后一路追。把节点链路的发送队列从 256 加到 4096（32KB/链路）之后丢帧归零，钳制次数降到 418。

    这条的教训是：**"可以丢"和"随便丢"是两件事**。广播帧丢了无所谓，输入帧丢了会变成位置偏差。当前实现还没有区分优先级，靠的是"队列足够大以至于几乎不丢"——真要上量，应该把输入帧和广播帧分成两条链路。

3. **迁移后的 `foreign` ID 不回收就等于泄漏**。实体在 n2 死掉时，n2 的分配器发现这个 ID 不属于自己的分区，只能忽略。第一版就停在这里，结果是 n1 的 `live` 永远涨（实测一次压测留下 95 个）。加了 `MsgReleaseID` 之后账才平。

4. **`Assign` 只能在本节点的场景里散列**。否则玩家一登录就被分到别的节点的场景，入场需要一次"请对方替我建实体"的 RPC——那是一条全新的路径，而且玩家一上线就跨进程，没有任何收益。把跨进程限制在"走过去"这一个动作上，复杂度才收得住。

复现：

```bash
./bin/server.exe -node n1 -node-addr 127.0.0.1:7003 -world configs/world-2node.json -gate-addr :7001 -admin-addr :7002 -mobs 100 &
./bin/server.exe -node n2 -node-addr 127.0.0.1:7103 -world configs/world-2node.json -gate-addr :7101 -admin-addr :7102 -mobs 100 &
./bin/bot.exe -n 200 -addr 127.0.0.1:7001 -duration 60s -move 100ms -walk x -min-x 40 -max-x 1500 &
./bin/bot.exe -n 200 -addr 127.0.0.1:7101 -duration 60s -move 100ms -walk x -min-x 40 -max-x 1500 &
```

### 6.10 服务发现（M3.4 实测）

6.9 跑通之后，全世界的节点成员还写在 `configs/world-2node.json` 里，每个节点各持一份、内容必须完全一致。这带来三个具体后果：

| 场景 | 后果 |
|---|---|
| 加一个节点 | 要改**所有**节点的配置文件并逐个重启，漏改一个就出现"半个世界"——那块地有人声明、没人承载 |
| 一个节点挂了 | 其它节点不知道，玩家走到边界照样发起迁移，3 秒超时回滚，每帧重试 |
| 换一个地址 | 同上，注册表里的地址和实际进程对不上，只能靠改文件 + 重启 |

M3.4 把"成员是谁"从启动参数里拆出来，但**没有**把整个世界交给注册中心。

#### 配置是期望，注册中心是实际

这是整节最重要的一句话。职责这样切：

```
配置（configs/world-3node.json）   期望：谁承载哪块地、每个节点的 ID 槽位
注册中心（discovery）              实际：谁现在活着、它的链路地址是什么
Topology                           投影：把两者叠起来，得到"这块地现在能不能过去"
```

为什么不把场景归属也放进注册中心：**场景搬家要迁移玩家**。那是一个需要计划、观察、能回滚的运维动作，不能由一次心跳抖动触发。把"谁该管哪块地"保持声明式、只让"谁还活着"动态化，才是能安全热更的组合。

投影的结果直接体现在路由上：主人不可达的地块从 `Route` 里消失，玩家走到边界被夹住，而不是发起一次注定超时的迁移。

#### 租约，而不是"注册 + 注销"

`Register` 写一条带时间戳的记录并按心跳续期，读的一方丢掉超过 TTL 的记录：

```
写记录   = put 带 lease
心跳续期 = keepalive（改写 ts）
过期     = lease 到期
扫目录   = range 带 prefix
```

为什么不能只做"注册 + 注销"：进程被 `kill -9`、机器掉电、容器被杀时根本来不及注销。只有"一段时间没心跳就判死"能覆盖这些情况。优雅下线才走撤销（`unregister()` 立刻删记录 + 移除文件），让邻居马上看到，而不是白等一个 TTL。

`internal/discovery` 只暴露两件事：

```go
Register(ctx, Node{Name, Addr}) (撤销函数, error)   // 我活着
Watch(ctx) <-chan View                             // 别人谁活着（整份快照）
```

视图是**整份快照**而不是增量事件：成员数是个位数，快照幂等、可重放、不会因为漏掉一条事件而永久错乱。视图比较刻意忽略心跳时间——否则每次心跳都被当成"成员变更"，调用方会以为集群在抖。

#### ID 步长必须固定，槽位必须稳定

这是让"加节点不用重启"真正成立的那一步，也是这一节唯一有数学的地方。

M3.3 的规则是 `id = seq × stride + offset`，其中 `stride = 节点数`。节点数变了，步长就变了，而**已经发出去的 ID 在新步长下的同余类会变**：

```
stride=2  n2(offset 1) 的第 103 个号 = 103×2+1 = 207
stride=3  n1(offset 0) 的第  69 个号 =  69×3   = 207   ← 撞号
```

撞号的后果不是"报个错"，是客户端把两个人认成一个人：A 死了，B 的血条消失。而且它是**静默**的，只在某个节点扩容后的某一天出现。

解决办法是把步长从"当前节点数"改成"槽位上限"，一次定死：

```json
{ "maxNodes": 4,
  "nodes": { "n1": "...", "n2": "...", "n3": "..." },
  "slots": { "n1": 0, "n2": 1, "n3": 2 } }
```

- `stride` 恒等于 `maxNodes`，永不变化
- `offset` 是节点的**固定槽位**，新节点只拿空槽位，已有节点的 offset 一个字节都不变
- 单体/老配置不写 `maxNodes`/`slots` 时，退化成"按节点名字典序"，与 M3.3 完全一致

代价是 ID 空间稀疏 `stride` 倍（槽位 4、1 万实体 → 高水位 4 万，每组件池 160KB）。这个代价换掉一整类"扩容引发的静默撞号"，值得。

配套改动：`IDOwner` 的反查从"排序表下标"改成"`id % stride` → 槽位表"，空槽返回空串（宁可漏一个 ID，也不要把回收指令发给错误的节点）。

#### 实测：四个阶段

一个节点先跑，邻居后到，邻居被杀，邻居重启——全程 n1 **没有重启过**（uptime 173 秒连续）。

| 阶段 | 操作 | 结果 |
|---|---|---|
| A 缺席 | 只启动 n1，100 机器人 15s | 登录 100/100、`alive=[n1]`、可达地块 1/3、切场景 **0**、迁移失败 **0**、`moveBlocked=1079` |
| B 热加入 | n2/n3 后启动（n1 uptime 43s） | n1 日志 `joined=[n2 n3] scenes=1→3`；240 机器人 30s：登录 240/240、迁出 50 / 迁入 50、切场景 50、失败 0、实体 100/100/100 |
| C 崩溃 | `kill -9` n3 | n1 **2.7s**、n2 **3.1s** 内 `lost=[n3] scenes=3→2`；80 机器人 20s：切场景 0、迁出停在 25、失败 **0**、`moveBlocked` 0→1616 |
| D 归队 | 重启 n3 | 4s 内 `joined=[n3] scenes=2→3` |

阶段 C 那一行是整节的结论：**掉线的邻居不会产生失败的迁移，只会变成一堵墙**。如果只做"注册"不做"投影到路由"，玩家会在边界上每帧发一次 Prepare、3 秒超时、再发，日志被刷满，人卡在原地抖动。

mesh 计数在全程保持 `dropped=0 / sendFail=0 / dialFail=0`；RTT 1.0~2.0ms（三个节点 + 240 机器人同机 4 核，比 M3.3 双节点时更低，因为每节点负载摊薄了）。

ID 账目：`stride=4 offset=0`，全部 ID 落在 4 的同余类上，`highWater=800`、`allocated=200`、`reused=80`——扩容后旧 ID 的含义没有被改写。

优雅关停三个节点后，注册目录**自动变空**（`unregister` 删记录），退出码 0。

#### 三个坑

1. **读到了写了一半的 JSON**。第一版直接 `os.WriteFile` 覆盖记录，读的一方偶尔解析失败，那个节点被判死——每秒都可能发生一次，表现为成员随机闪断。改成"写临时文件 + rename"（原子替换）后消失。

2. **TTL 不能等于心跳间隔**。TTL 取 3 倍间隔（默认 1s 心跳 / 3s TTL）：等于间隔时，一次 GC 停顿或者一次调度延迟就会让自己的记录过期，成员视图开始抖，而"抖"在拓扑上表现为玩家走到边界偶尔过不去——一个看起来完全像玩法 bug 的现象。

3. **`rejectedMoves` 会把"贴墙"算成"作弊"**。阶段 A 里它涨到 1036，看起来像 100 个超速客户端，实际是玩家顶着 x=512 的墙走：客户端仍按"我在走路"上报坐标，服务端先按速度钳制（rejected +1），再发现越界夹回。加了 `moveBlocked` 单独计数后判读方法是看比例——两个一起涨 = 有一堵墙；只有 rejected 涨 = 真的超速。

#### 复现

```bash
# A：只起 n1，玩家走到 x=512 会被夹住，切场景数为 0
./bin/server.exe -node n1 -node-addr 127.0.0.1:7003 -world configs/world-3node.json \
  -gate-addr :7001 -admin-addr :7002 -mobs 100 -disc file -disc-dir run/m34/nodes
# B：n2/n3 后起，n1 日志里出现 joined=[n2 n3]，之后跨界恢复正常
# C：kill -9 n3，3 秒内 n1 日志出现 lost=[n3] scenes=3→2
./bin/bot.exe -n 80 -addr 127.0.0.1:7001 -duration 30s -move 100ms -walk x -min-x 40 -max-x 1500
```

#### 遗留

- **etcd 适配器还没有实现**。抽象（`Registry` 接口）和语义（租约、整份视图、幂等应用）都已经跑通，但本机没有 etcd 也没有容器，我不想交付一份没在真集群上跑过的客户端。接入时只需要实现同一个接口的 `Register`/`Watch`，上层一行不改。
- 文件注册中心只适用于单机多进程或共享卷：文件系统没有一致性保证，两个节点可能同时看不到对方。跨机房必须换 etcd。
- 节点掉线时，它承载的玩家没有接管策略（实体随进程一起消失）。这是 M3.5 解决的第一件事，见 6.11。

### 6.11 世界重分区（M3.5 实测）

M3.4 让"谁活着"可以热更，但"谁管哪块地"还写死在配置里。那个缺口有两个具体后果：

```text
扩容   新节点起来了却没有地 —— 玩家进不去，等于白加机器
掉线   崩溃节点的地变成一堵墙 —— 玩家走到边界被夹住，永远过不去
```

#### 两种动作，代价差一个数量级

| 动作 | 前提 | 要搬的东西 | 代价 |
|---|---|---|---|
| 搬迁 `MoveScene`（主人活着） | 地上的实体还在 | 每一个实体走一次 Commit | 与人头数成正比 |
| 接管 `Reclaim`（主人已死） | 实体随进程一起消失 | 只改拓扑 | O(1) |

接管是搬迁的退化情形——"要搬 0 个人"。两条路径共用同一套两阶段提交，区别只在中间要不要排空。

#### 为什么不能让两边各改各的拓扑

```text
n1 认为 scene3 是自己的，n2 也认为是自己的
→ 玩家从 n1 走进去，n1 收下；从 n2 走进去，n2 也收下
→ 同一个场景两个写者，"单写者"这个前提当场失效，实体表会分叉
```

所以拓扑切换必须是**一个有先后的动作**：

```text
源(协调者)                目标                     其它节点
   │  Prepare ───────────▶ 建 standby（能收 Commit，不在路由里）
   │  ◀──────────── Ready
   │  ① 置 draining（拒收迁入）
   │  ② 每帧搬 64 个实体 ──▶ Commit ×N（复用 land()）
   │  Activate ───────────▶ 接进路由（topo.adopt）
   │  ◀─────────── Activated
   │  ③ 广播 Move ────────────────────────────────────▶ 改路由
   │  ④ 自己改路由 + 退休（loop 退出，场景对象销毁）
```

①之后源场景一个实体都不剩，收到迁入会拒（draining），所以「目标已接、别人还不知道」的那段窗口不会分叉。

#### 唯一一条硬规则：搬人之前可以回滚，开始搬之后只能往前

`Prepare` 阶段一个人都没动，被拒或超时就干净撤销（`draining=false`，目标销毁空壳）。一旦进入排空，任何回滚都会造成"一部分人在 A、一部分人在 B，而这块地只能有一个主人"。

所以：

| 阶段 | 失败处理 | 理由 |
|---|---|---|
| Prepare | 重试 3 次后中止 | 零成本，人能留在原地 |
| 排空 | 本帧停下，下一帧继续，永不中止 | 先发后摘，实体没摘就还在 |
| Activate | 无限重发 | 人已经全在对面，中止等于丢人 |

这条规则也解释了为什么排空不走 `tryHandover`：那条路要靠 `Route` 找到对面，而重分区期间路由还指向自己。这里直接构造 `Commit` 投给目标——落地仍然复用 `land()`，不写第二套落地逻辑。

#### 排空为什么要限速

`evacBatch = 64` / 帧 = 1280 个/秒。不是为了省 CPU，而是给节点链路的发送队列（4096）留出空间：一帧把 5000 个 Commit 塞进去，队列满之后 `TrySend` 丢掉一部分，结果就是"搬了一半、另一半还在原地"。限速之后拥塞点暴露成"搬得慢"，而不是"搬丢了"。

发送失败时**不 detach**——实体完整留在源场景，下一帧重试。这和 `tryHandover` 的"先问再摘"是同一条原则的两个变体：**任何可能失败的步骤，都要排在不可逆的那一步之前**。

#### 实测

三节点（`configs/world-3node.json`），每场景 100 只怪，机器人沿 x 轴来回走。

| 阶段 | 操作 | 结果 |
|---|---|---|
| A 搬迁 | n3 的 scene3（169 实体）搬到 n1 | **223ms** 完成；moved=169 / left=0；三节点 `s3@n1` 一致；迁移失败 0 |
| B 崩溃接管 | `kill -9` n1，n2 自接 scene3 | 100 只怪重新填充（地上已无人）；`s3@n2` 一致 |
| C 第三方接管 | n2 发起，把 n1 的 scene1 交给 n3 | **509ms**（含一次向死节点拨号失败）；两边 `s1@n3` 一致 |
| D 接管后通行 | 60 机器人从 n2 走进两块接管地 | 登录 60/60、切场景 10、失败 0、`moveBlocked=0` |

D 是最能说明问题的一行：接管完不只是"拓扑说这地有主了"，而是**玩家真的能走进去**——`moveBlocked=0` 意味着没有人被夹在边界上。

#### 三个坑

1. **接管方又刷了一份怪**。场景工厂里有"刷 100 只怪"的逻辑，接管时照跑一遍，169 个实体的地搬过去变成 269。修法是给 `SceneSpec` 加一个运行期字段 `Incoming`（有多少实体正在搬进来），工厂据此决定要不要预填充：**正在搬迁的场景会把自己的怪带过来，接管一块空地的才需要重新刷**。

2. **`Activated` 没设 `OK`，发起方以为被拒绝**。`SceneCtl.OK` 默认 false，成功路径忘了置 true。后果极其安静：目标节点已经把地接管了，发起方却走进 `if !act.OK` 分支返回，**自己不改路由**——两个节点对同一块地记着不同的答案，日志里只有一行 `activate refused reason=""`。这是"BOOL 字段的零值恰好是这个分支的错误答案"的经典翻车。

3. **`NoClient` 用 `client == nil` 判断，把跨进程玩家当成 NPC**。跨进程搬玩家时 `payload.client` 本来就该是 nil（换成了 `ClientRef`），用它判空会让落地侧跳过 `resolveRef`，玩家落进新场景却不切路由——表现是客户端发来的移动包全打到旧场景。改成按 `kind != KindPlayer` 判断。

#### 复现

```bash
# 起三节点（各有自己的地）
./bin/server.exe -node n1 -node-addr 127.0.0.1:7003 -world configs/world-3node.json \
  -gate-addr :7001 -admin-addr :7002 -mobs 100 -disc file -disc-dir run/m35/nodes
./bin/server.exe -node n2 ... -gate-addr :7101 -admin-addr :7102 ...
./bin/server.exe -node n3 ... -gate-addr :7201 -admin-addr :7202 ...
# 搬迁：把 n3 的 scene3 交给 n1（223ms）
curl -X POST 'http://127.0.0.1:7202/admin/repartition?scene=3&to=n1'
# 接管：kill -9 n1 之后，让 n3 拿下它留下的 scene1
curl -X POST 'http://127.0.0.1:7102/admin/repartition?scene=1&to=n3'
# 进度看 /admin/state 里对应场景的 move 字段（to / phase / moved / total）
```

#### 遗留

- **`Move` 广播不是事务**。漏收的节点会保留旧路由，表现是玩家走到那块边界时 Admit 投给了一个已经没有这个场景的节点、3 秒超时后被夹住。这是 M3.6 要解决的事，见 6.12。
- **没有自动重分区**。什么时候搬、搬到哪，目前完全由人决定。真正的调度器要看负载（`Chunks()` 已经带 `entities` / `load`），还要能回滚。
- **搬迁期间那块地的边界不可穿越**。源场景 draining 会拒收，通常只有几十到几百毫秒。要消掉这段窗口就得让两个场景同时接受写入——那正是重分区要避免的事。

### 6.12 拓扑对账（M3.6 实测）

M3.5 的重分区靠一条广播告知全网。广播会丢：节点链路队列满时丢当前帧、链路正好断、对端那一刻还没起来。

丢一条广播的后果不是报错，而是**静默的永久不一致**。漏收的节点手里那份拓扑和别人的长得一样"合理"，只是旧了。它没有任何办法知道自己漏了——因为拓扑没有"我该是什么样"的参照物。

一个具体的反例（这次实测真的跑出来了）：

```
t0  n1/n2/n3 各持一块地，view 一致
t1  n3 把 scene3 交给 n1         → 广播到 n1、n2，都收到了
t2  kill -9 n2
t3  n3 接管 n2 留下的 scene2     → 广播到 n1；n2 不在，无从通知
t4  n2 重启，读配置：scene2 是我的
    → n2 建了一个场景 + 100 只怪，而 n3 那边也跑着一份
    → 同一块地两个写者，实体表开始分叉
```

`n2` 不知道自己错过了什么，`n3` 也不知道 `n2` 手里有一份副本。这种情况下再多的"更可靠的广播"都救不了——需要的是**可比较的状态**。

#### 做法：版本号 + 定期互换整份视图

每块地带一个归属版本号，**只在归属变化时加一**（不是每次广播加一）。然后每 2 秒和所有节点互换一次整份拓扑摘要，谁新谁赢：

```
广播   快：毫秒级生效，绝大多数情况下一次就够
对账   准：漏了也在两个周期内补回来，不需要人介入
```

版本号只在归属变化时递增这一点很关键。如果每次广播都加一，两个节点各自广播就会互相"证明"自己更新，版本号变成噪音，谁也不服谁，对账退化成永远相信最后说话的那个人。它回答的是"这块地换过几次主人"，不是"我发过几条消息"。

比较规则只有三条，广播和对账共用同一套（否则会出现"广播接受、对账拒绝"的僵局）：

| 比较结果 | 动作 |
|---|---|
| 对端 `ver` **更高** | 采用对端的归属，本地场景（如果有）退休 |
| 对端 `ver` **更低** | 把本方摘要推回去，限流 1 次/秒 |
| `ver` 相同、归属不同 | 取字典序小的节点名赢，**双方各自把版本 +1** |

第三条是唯一需要"裁决"的情形，它对应"一条 Move 丢在了路上"或者"两边各改各的"。做法不是协商，而是让两边**独立算出同一个结果**：都取 `min(ownerA, ownerB)`、都把版本加一。于是下一轮摘要相同，`verdictSame`，不再有任何动作。反过来如果写成"谁收到谁改"，两边会互相改写，永远收敛不了。

两个刻意的例外：

- **正在搬迁/接管的场景跳过对账**。搬迁的中间态（目标已接、源还没摘）在拓扑上看起来正是"两边都说是自己"，对账这时候裁决会把这一刻坐实成永久状态。这两个标志（`Scene.Moving()` / `Scene.Standby()`）是原子的，专门给对账协程看——直接读 `s.evac` 是数据竞争，那个字段由 tick 协程独占。
- **退休必须回收 ID**。见下面的坑 1。

#### 退休：丢掉一份副本，而不是留着两个写者

对账发现"这块地归别人了，而我手上有一个场景"时，唯一正确的动作是把它停掉。丢掉地上的实体是对的——那些是本进程刚按配置造出来的副本，真正活着的那份在对面；留着才是灾难。

但停场景不能从外面调 `Stop`：`entities` 是无锁 map，只有 tick 协程能碰。所以退休走一条消息（`msgRetire`），由 tick 协程清空实体（走的是玩家正常下线那段 `removeEntity`，会把 ID 还回分配器 / 通知所有者），然后自己退出循环。

#### 实测（三节点，每场景 100 只怪）

| 阶段 | 操作 | 结果 |
|---|---|---|
| 基线 | 三节点启动 | 三份摘要完全一致，`vers` 全 0，`applied=0` |
| 搬迁 | n3 的 scene3 → n1 | 三节点 `vers[3]=1`、`s3@n1` 一致；n2 走**广播**（`applied=0`） |
| 崩溃接管 | `kill -9` n2，n3 接管 scene2 | n1/n3 `vers[2]=1`、`s2@n3` 一致 |
| **重启归队** | n2 拉回来 | **37ms** 后 n2 收到 n1 的摘要：`scene2@n3 ver=1`、`scene3@n1 ver=1`；57ms 时 `scene purged scene=2 entities=100`；`applied=2 retired=1`，三节点 `chunks` 再次一致 |
| ID 账目 | 退休之后 | n2 `live=0 cooling=100`（100 个怪 ID 全部回到冷却队列，没有泄漏） |
| 通行 | 60 机器人从 n3 来回穿越两块地 30s | 登录 60/60、切场景 19、**迁移失败 0**、`moveBlocked=0` |

最后两行是这轮的重点。**重启的节点在 37 毫秒内就把自己纠正了**，而它错过的是两条广播、跨了两个重分区动作。`live=0` 说明退休没有变成 ID 泄漏——这一条第一版是错的，见坑 1。

顺带得到一个意外的观察：这一次 **对账比广播先到**。n3 的 `broadcastMove` 串行遍历对等节点，先给已经死掉的 n2 拨号，失败路径卡了将近 1 秒，于是排在后面的 n1 反而先收到了周期性摘要（`16:20:16.100` 对 `16:20:16.569`）。修法是**已经判死的节点不发广播**，反正它收不到，回来时 discovery 会触发一次定向摘要。

#### 三个坑

1. **退休场景不回收 ID，`live` 永远停在 100**。第一版 `retireScene` 直接 `Stop`，实体表连同 ID 一起没了：代理进程的 `live=100`、`allocated=100`、`cooling=0`，100 个怪 ID 永久泄漏。M3.1 花力气做的冷却回收在这条路径上等于没做。改成在 tick 协程里逐个 `removeEntity` 之后 `live=0 / cooling=100`。
2. **广播被死节点的拨号拖慢**。串行广播里一个死节点会给排在它后面的活节点带来最多 1 秒延迟（`dialTimeout`）。因为对账兜底，这个延迟不影响正确性，但它让"快路径"比"慢路径"还慢，是可观测性上的坏味道。
3. **启动窗口**。重启节点按配置建场景是**必然**发生的（配置是期望），纠正它需要一次摘要往返。在网关开出去之前给一个 300ms 的窗口（`firstDigestWindow`），能把"玩家刚落地的场景被退休"从大概率事件压到接近零——但不是消除。真正的解法是拓扑持久化，属于 M5。

#### 复现

```bash
# 三节点 + 共享注册目录
./bin/server.exe -node n1 -node-addr 127.0.0.1:7003 -world configs/world-3node.json \
  -gate-addr :7001 -admin-addr :7002 -mobs 100 -disc file -disc-dir run/m36/nodes
# ... n2 / n3 同理
curl -X POST 'http://127.0.0.1:7202/admin/repartition?scene=3&to=n1'   # 搬迁
# kill -9 n2，再让 n3 接管它留下的地
curl -X POST 'http://127.0.0.1:7202/admin/repartition?scene=2&to=n3'
# 重启 n2：37ms 内日志出现 "topology: adopted peer view" + "scene purged"
# 对账统计看 /admin/state 的 world.topology 字段
```

#### 遗留

- **拓扑不持久化**。重启的节点永远从配置重建，然后靠对账纠正。中间那 37ms 里它认为自己是主人，如果这时候有玩家登录（网关还没开，所以实际不会）就会落到一块马上要被退休的地上。
- **摘要是全量的**。节点数 N、场景数 S 时，每个周期 O(N·S) 条消息、每条约 30S 字节。个位数节点完全无所谓，上百节点要改成增量（只发版本变化的部分）。
- **被退休的地上如果有玩家，会被直接清掉**。理论上不该发生（入口窗口 + 单写者），但真发生了就是掉线，而不是被安全地转到新主人那边。要做得好需要在退休前把人迁走——那是把重分区的排空逻辑套一遍，成本不低。
- **仍然没有自动重分区**。对账只保证"大家看法一致"，不保证"看法合理"。（M3.7 已补上自动调度，见 6.13。）

### 6.13 自动重分区调度（M3.7 实测）

M3.5 把"手动搬一块地"跑通了，M3.6 保证"大家的看法一致"，但**什么时候该搬、搬到哪**仍然要人盯。一个节点挂掉被接管之后，剩下的地就一直歪着——n1 拿了两块、n2 一块，直到下一次人为介入。M3.7 让每个节点自己看着拓扑，**只动自己拥有的地**，把过载的那块搬到最空的活节点上。

#### 决策模型

调度器跑在每个节点上（组件名 `auto-rebalance`），每 `eval` 周期（默认 5s）做一次纯函数式评估：

1. **聚合**：从 `Chunks()` 拿当前归属快照，按场景 id 去重，数每个**活**节点持有的场景数。死节点的场景不计入分母——那块地正处在被接管的中途，数它会让公平份额虚高。
2. **公平份额**：`fair = totalScenes / aliveNodes`，`allowance = ceil(fair)`（有余数时少数节点多持一个）。允许 `slack`（默认 0）的额外裕度，避免在 2/2/1 这种已经最优的分布上微调。
3. **触发**：仅当"我持有的场景数 > allowance + slack"才考虑搬。**只有超载节点自己发起**——因为一个场景只有一个主人，只有主人能排空（`MoveScene` 的本地分支），第三方只能接管死节点。
4. **选目标**：活节点里持有场景最少的（不含自己）；同样少时取名字字典序小的，保证确定性。
5. **硬条件：搬过去不能制造新的最大**。`target.hold + 1 < myScenes` 才允许搬。等号都不行——等号意味着把最大从我这儿挪到目标那儿，总数没改善，白搬一趟还制造一次版本号变更和广播。这条是防振荡的核心：5 个场景 3 个节点从 3/1/1 收敛到 2/2/1 之后就停，不会在 2/2/1 和 1/2/2 之间来回。
6. **选场景**：在候选里（我持有的、没在搬、没在 standby、过了冷却的）按"**和目标地块相邻 > 实体数最多 > id 最小**"排序。相邻优先让搬完之后路由表还是连续的，玩家穿越边界少一次跨节点跳。

#### 不做的事（边界）

- **不预测**。只看当前快照，不根据趋势预搬——预测错了比不搬更糟。
- **不拆场景**。一个场景就是一个 Chunk（512m），最小搬迁单位。
- **不强行均**。能接受 1 个场景的不均衡（5/3 收敛到 2/2/1 即停）。
- **不接管死节点的地**。死节点的场景回收是 `MoveScene` 的第三方接管路径（M3.5），那是"这块地的主人没了"的更大决策，主人可能只是网络分区暂时不可达。自动接管会和回来后的主人撞车，留给显式触发更安全。调度器只搬**活主人**手里**自己**的超载场景。

#### 并发与回滚

- **一次只搬一个**：发起搬迁后置 `inflight`，下一次评估若该场景尚未切主（`PeerOf` 仍是自己）且未过冷却，直接 `defer`，不再发第二个并行搬迁。判"落地"用 `PeerOf != 自己`（搬走）或"超过冷却仍在我手里"（多半是 prepare 失败被 `abortEvacuate` 回滚），**不**用 `Moving()`——`MoveScene` 返回 nil 之后、tick 协程处理 `msgBeginMove` 之前的窗口里 `Moving()` 还是 false，拿它判会把刚发起的搬迁误判成已完成。
- **冷却**：同一场景两次搬迁至少间隔 `cooldown`（默认 15s），必须大于一次搬迁耗时（~300ms）加裕度，否则上一轮还没落地、下一轮又对同一场景发起 `MoveScene` 会被自身的 `Moving()` guard 拒掉，统计上像在反复失败。
- **回滚**：调度器本身没有回滚路径——它只调 `MoveScene`，搬迁的回滚（prepare 失败→`abortEvacuate`）已经在 M3.5 里实现。调度器层失败的 `MoveScene`（邮箱满、已在搬、目标是自己）会回滚 `inflight` 和冷却，下一轮可重试。

#### 实测：5 场景 3 节点自平衡

`configs/world-5scene-3node.json` 故意制造不均衡：n1 持 scene 1/2/3（300 实体），n2 持 scene4，n3 持 scene5。三节点用 file 发现互连，开 `-auto-rebalance -rebalance-eval 3s`：

| 时刻 | 事件 |
|---|---|
| +0s | 三节点互发现，n1 看到 scenes=5，自己持 3 块 |
| +13s（首次评估） | n1 调度器：`auto-rebalance move scene=3 to=n2 ents=100 from=3 fair=2`（scene3 与 n2 的 scene4 相邻） |
| +13.19s | n1 drained 100 实体（50ms）→ activating → retired（决策到退休 **190ms**） |
| +13.14s | n2 `scene adopted scene=3 from=n1 ver=1`，handIn=108（100 搬入 + 8 穿越迁入） |
| 之后 5 个评估周期 | 三节点都 `balanced: own 2/5`，**attempted 不再增长** |

收敛结果：n1=2（scene1,2）、n2=2（scene3,4）、n3=1（scene5），实体守恒各 100，三节点拓扑一致。40 机器人沿 X 轴穿越 5 场景 25 秒：`logined=40 failed=0 sceneSwitches=11 handoverFails=0 moveBlocked=0 avgRTT=1.9ms`。

#### 踩的坑

- **inflight 误清**：最初用 `Moving()` 判"搬迁是否落地"，结果 `MoveScene` 返回 nil 到 tick 处理 `msgBeginMove` 之间有个 ~1ms 窗口 `Moving()` 还是 false，下一次评估立刻把 inflight 清掉，于是对**另一个**场景又发起一次搬迁——两个搬迁并行往同一目标节点发 Prepare，版本号连跳两次，日志里看着像抽风。改成"切主（`PeerOf` 变了）才算成功落地"之后才稳定。
- **公平份额把死节点数进去**：死节点的场景数计入分母时，`totalScenes/alive` 把活节点都算成"低于平均、不用动"，调度器在 n3 死掉后完全不动。改成只数活节点持有的场景后才正确触发。
- **搬迁相邻性**：一开始按"实体最多"挑场景，结果把 n1 最左边的 scene1 搬到 n2，搬完之后 n2 持有 [0,512) 和 [1536,2048) 两块飞地，路由表不连续。改成"和目标地块相邻优先"后，搬的是 scene3（紧贴 scene4），结果 n2 持有连续的 [1024,2048)。

### 6.14 链路优先级与下行批量合并（M3.8 实测）

M3.3 引入节点链路时，靠的是"把队列加到 4096 足够大、几乎不丢"来回避拥塞（见 6.9 第 2 条教训）。但那条注释里已经点破：**输入帧和广播帧共用一条链路、共用一个队列，上量之前该拆开**。M3.8 把这个 TODO 补上，分两层做。

#### 第一层：双优先级发送队列

节点链路上跑着两类语义完全不同的消息：

| 类别 | 消息 | 丢一帧的代价 |
|---|---|---|
| 控制 / 握手 | Prepare、Ready、Commit、SceneCtl、TopoDigest、Rebind、ReleaseID | 一次失败的迁移（3 秒超时回滚）或全网路由永久不一致 |
| 数据 | Relay（上行转发）、ClientSend/ClientBatch（下行广播） | 玩家少看一次位置更新，下一帧补上 |

原来两类消息进同一个 `sendq`，拥塞时 `TrySend` 丢当前帧，**丢到的可能是握手**。修法是在 `net.Conn` 里开两条队列：

- `sendq`（高优先）：控制/握手
- `sendqLow`（低优先）：数据

写协程先非阻塞排空高优先队列，再处理低优先。`mesh.Send` 按消息号分类（`isControlMsg`：只有 `MsgRelay`/`MsgClientSend`/`MsgClientBatch` 是数据，其余一律高优先——默认高优先是刻意的，宁给新加的握手类消息走快通道，也不能让一条漏分类的握手和广播帧一起被挤掉）。

分类逻辑为什么不放在业务层（world/gate）而是 mesh：分类只依赖消息号，mesh 是唯一既知道"这是哪条链路"又知道"这条消息该不该优先"的地方。放业务层会让每个调用点都得记住"这条要高优先"，漏一处就是 bug。

#### 第二层：跨节点下行批量合并

优先级解决"丢谁"，批量合并解决"发多少次"。跨节点玩家的每个广播包都是一条 `MsgClientSend`，单独组帧 + 过队列 + 抢锁。实体上千时这开销线性放大。修法：

- 新增 `MsgClientBatch` 消息：把多条 `ClientSend` 打包成一条。
- `remoteClient.Send` 改走 `mesh.SendClientSend`（零拷贝，直接传结构，不做 encode→decode 往返）。
- `Mesh` 每个 link 挂一个聚合缓冲，`flushLoop` 每 2ms 扫一次，把攒够的批合并成一条 `MsgClientBatch` 发出；单批超 256 条立即冲刷（防极端 tick 攒出巨批）。

2ms 窗口比一帧（50ms）短一个数量级，延迟损失可忽略，换来的是 N 次组帧/锁竞争压成 1 次。接收端 gate 拆开逐条写 socket，客户端无感知。

#### 实测（三节点，每场景 100 怪，200 机器人沿 X 轴穿越）

| 指标 | 数值 |
|---|---|
| 批量合并 | n2 侧 `batched=14622`、`batchedFlush=491`，**平均每批 ~30 条** |
| 拥塞丢帧 | `dropped=0`、`controlDropped=0`（握手零丢失） |
| 通行 | 200 机器人登录 200/200、切场景 45、失败 0，avgRTT 5.7ms |
| 搬迁兼容 | 批量合并后重分区 scene3→n1 全程 151ms，100 实体，握手不受影响 |

`controlDropped` 是关键观测：理想恒为 0。如果某天它非 0，说明拥塞已经压到高优先队列了，这时才需要真正拆两条链路，而不是继续加队列。

#### 踩的坑

- **flushLink 用 addr 当 node 去查表**：第一版 `flushLink` 用 `l.addr` 调 `sendRaw`，但 `sendRaw` 是按 `links[node]` 查表的，addr 是地址不是节点名，会 `ErrUnknownPeer`。link 结构补一个 `name` 字段（节点名）解决。
- **批量合并别在 world/gate 层做**：最初的直觉是在 `remoteClient` 里攒批，但 `remoteClient` 每个玩家一个实例，攒批状态会散落；而且跨节点的下行不止 `remoteClient` 一条路（还有 kick、notice 等）。收敛到 mesh 层——所有跨节点下行都汇聚到 `msh.Send` 这一个点——才是一处改动覆盖全部路径。
- **测试别断言异步广播的收敛结果**（本里程碑顺手修掉的一个 M3.7 遗留 flaky）：`SceneOpMove` 是尽力而为的广播，第三方节点（n3）靠它异步更新路由。`TestSchedulerMovesOverloadedScene` 原来只等"源退休 + 目标上线"就断言 n3 也收敛，`-count=50` 下 ~12% 概率读到 n3 还停在旧路由（广播还在路上）。修复是断言前用 `waitFor` 等所有节点都收敛——这和产品代码无关，纯粹是测试把"异步收敛"当成了"同步完成"。

### 6.15 战斗管线：技能 + 伤害结算 + Buff（M4 实测）

**问题**：M3.x 做完了"世界能跑、能搬、能自愈"，但一直没有"玩"——玩家进了世界只能走路看怪，怪的血条会自己回满，谁也没法打谁。creature 包早就埋好了伏笔："要加战斗，就在这个包里加一个 combat 包和一个 StageLogic 系统"。

**做法**：新建 `internal/game/combat`，把"打怪"这条最小闭环补上，但把 skill/buff 两个子包**并进 combat**而不是拆三个包——技能种类只有个位数、Buff 只有四类，为一个 3 个技能的注册表和 4 个枚举拆两个包，是过度设计。等真有了技能树/连招/驱散再拆。

核心设计：

1. **技能是静态描述符 + 运行时 CD 状态**。`Skill` 描述符（ID/伤害/射程/CD/AOE）放进程级 `Skills` 表里查表，实体只存 `Combat.CDs[4]` 这个"下次可施放时刻"的固定数组。数组而非 map：技能 ID 连续、种类少，数组零分配且保持 `Combat` 结构定长（连续内存）。
2. **攻击走 mailbox，不走意图缓冲**。`Move` 走意图缓冲（后写覆盖先写，见 6.5），但攻击要改实体状态、可能移除实体，是单写者模型下的写操作，必须 `post(&msgAttack)` 进 mailbox 由 tick 协程串行执行。`world.Attack` → 回调玩法包注入的 `SetAttackHandler`。
3. **伤害公式一条线性链**：`(技能伤害 × 攻击力/100 − 防御) × 增伤 × 减伤`，Buff 修正用乘法叠加。刻意不做暴击/元素/护盾——那是 pipeline 化之后的事（4.6 的"伤害管线"抽象），现在只证明"组件 → System → 结算 → 广播 → 回收"整条链路通。
4. **Buff 是变长列表组件**（`CBuff = Define[[]Buff]`），单独一个组件而不是塞进 Combat——塞进去 Combat 就带切片字段，破坏连续内存。四类效果：增伤/减伤/中毒/回血，250ms 一个 tick 结算（20Hz 帧降成 4Hz 结算，和 creature 的回血同款"低频闸门"写法）。
5. **死亡 = `Scene.Leave`**：击杀后直接走既有的离场路径（广播 Leave、摘索引、清组件、回收 ID），不新写一条"死亡移除"——那是 M3.1 就做好的 ID 回收，战斗复用而不是重造。

**协议**：新增 `MsgC2SAttack`（上行：目标 ID + 技能 ID，**不带伤害数值**——伤害由服务端算，客户端只表达意图）和 `MsgS2CCombatHit`（下行：攻击者/受击者/伤害/剩余 HP/击杀标记），以受击者为圆心广播给视野内所有玩家。跨节点攻击复用 `MsgRelay` 加一个 `RelayAttack` kind（Relay 结构补 Target/Skill 两个字段），走既有的 Relay 通道而不是新开消息号。

**实测**（三节点，每场景 50 怪，100 机器人 `-attack`）：

| 指标 | 结果 |
|---|---|
| 伤害结算 | 25 秒 `hits=528`（每次命中广播一次 CombatHit），`kills=38` |
| 跨节点攻击 | 连接在 n1、实体落在 n2/n3，攻击经 `RelayAttack` 转发，`mesh.dropped=0` |
| 实体回收 | n1 scene1 怪 50→45（击杀 5 只被 `Leave` 回收），组件池 `combat.stats` 与 `creature.attr` 数量一致 |
| 稳定性 | 100/100 登录、`failed=0`、19 次跨场景切换、avgRTT 2~4ms |

**踩坑**：

- **AOE 必须单独结算主目标**：`Scene.ForEachNear` 会跳过目标自己（`id == e.id` 就 return），AOE 只遍历邻居会漏掉"被打的那个"。正确做法是主目标先 `dealDamage` 一次，再遍历邻居补溅射。这个 bug 单测就抓到了（AOE 测试里目标不掉血、邻居掉血）。
- **击杀后不能继续读目标组件**：测试里"打一下 → 读 `attr.Get(mob.ID()).HP`"会 panic，因为怪被一击秒杀后 `Leave` 把组件清了。压测/单测里要么用血厚的怪，要么先判 `Entity` 还在不在。
- **Buff tick 的闸门在测试里会挡路**：250ms 闸门用真实时间判断，测试里两次 `TickOnce` 间隔 < 250ms 就永远不结算。测试直接构造 `*resolver` 手动调 `buffTick` 并传可控时间，而不是依赖真实时钟。

### 6.16 存档与恢复（M5 实测）

**问题**：M3.6 对账解决了"运行期谁是最新"，但埋了一个伏笔——节点全挂重启后，拓扑版本号从 0 重新数。`topoReconcile` 的 `firstDigestWindow` 注释里写得很直白："真正的解法是拓扑持久化，那是 M5 存档的事。" 另外，怪物的属性、AI、战斗状态（Buff/CD）一关服就全没了，重启后只能重新刷一批"没有记忆"的怪。

**做法**：新建 `internal/world/save.go`，把存档拆成两层职责：

1. **实体状态**——复用迁移已经建立好的 `TransferCodec`。存档和跨场景迁移读的是同一份编解码逻辑，不存在两套格式漂移。为此把原来"单一 codec"的 `SetTransferCodec` 升级成 **codec 链**（`AddTransferCodec`）：creature 存属性+AI，combat 存战斗+Buff，各自产出一段字节，world 层用「u16 段数 + 每段 [u16 长度 + 字节]」拼成一个 blob。新增玩法包只需 `AddTransferCodec`，不动已有包的格式。
2. **拓扑归属 + 版本号**——把每块地的 owner/ver/rect 落盘，重启时回填版本号，让对账从盘里的版本继续，而不是从 0 重新数。

**单写者约束**：采集和恢复都要遍历实体表/组件/ID 分配器，这些都属于 tick 协程。所以 `SaveWorld`/`RestoreWorld` 走 mailbox 投 `msgSave`/`msgRestore`，由 tick 协程执行，调用方阻塞等结果（带 2 秒超时）。场景未 Start 时（没有 tick 协程、无并发）直接读，省一次 mailbox 往返。

**恢复语义**：只恢复**非玩家实体**（怪/NPC）——玩家的连接是运行时的，存档里没有它，重新登录时由 Gate 走 `EnterAt` 重建；否则会造出一批"没有连接、收不到包、也踢不掉"的僵尸玩家。归属**不改**——归属以配置为准（配置是期望），只回填版本号。

**原子落盘**：先写 `.tmp` 再 rename，和 `control/persist.go` 同一个理由——进程可能任意时刻被杀，直接覆盖会留下半截文件。

**接入**：`cmd/server` 加 `-save-dir` / `-save-interval`，注册 `saveComponent`（`core.Component`）。它排在场景之后、网关之前注册，这样 Start 时场景 tick 已在跑（能恢复），Stop 时（逆序）网关先停、存档后停（落盘时场景还在跑，能采集）。每节点一份存档文件 `world-save-<node>.json`（拓扑版本号、ID 分区、实体都是按节点分的）。存档优先：存在存档文件时跳过 `-mobs` 刷怪，从存档恢复。

**实测**：

单节点（50 怪，3 秒周期保存）：

| 验证点 | 结果 |
|---|---|
| 周期落盘 | 每 3 秒一次 `world saved reason=periodic`，怪的位置随 AI 游荡持续变化（Brain 状态在存档里） |
| 关服落盘 | `component stopped component=save cost=185ms` 在 `scene stopped` 之前，最后 `world saved reason=shutdown`，exit 0 |
| 重启恢复 | 无 `mobs spawned`（正确跳过刷怪），`world restored entities=50`，从存档恢复 50 只怪 |

两节点（各 20 怪，重分区后重启）：

| 验证点 | 结果 |
|---|---|
| 各自存档 | `world-save-n1.json` / `world-save-n2.json` 各自生成，拓扑 owner 正确 |
| 拓扑版本持久化 | 重分区搬场景 3（ver 0→1），存档里 `scene 3 owner=n1 ver=1` |
| 重启后对账纠正 | n1 恢复 ver=1，n2 重启后 ver=0，对账把 n2 纠正到 ver=1（n2 `applied=1`、n1 `pushed=1`） |

**关键结论**：最后一条是 M5 的核心价值——**没有拓扑持久化，n1 重启后 ver 也归零，两个节点都从 0 数，就失去了"谁更新"的判断依据**。版本号落盘让"先关后开"的节点不输在起跑线上。

**踩坑**：

- **归属不恢复、只恢复版本号**：重分区把地搬到别的节点后，重启仍按配置重建（配置是权威）。这是**有意**的语义——重分区是临时运维动作，重启回到配置定义的世界。但版本号必须恢复，否则对账在"配置 vs 存档"的归属差异上会反复误判。实测里 n1 恢复 ver=1、n2 配置 ver=0，对账用版本号裁决，没有冲突。
- **恢复要跳过玩家实体**：玩家的 client 是运行时的接口值，序列化不了也恢复不了。存档只存非玩家实体，玩家靠重新登录。这是 land 的迁移路径早就定下的约定，存档沿用。

### 6.17 审计 + RBAC + 拓扑热力图（M6.5 实测）

**问题**：控制面（M6）是"单机版"——`/admin/*` 完全裸奔，谁都能 `POST /admin/shutdown` 把整个区关掉，而且没有任何操作留痕。真要上生产，运维接口必须能回答两个问题：**"谁能动"** 和 **"谁动过什么"**。此外，多进程部署时想知道"哪块地负载最高、该拆了"，光看数字不够直观，需要一张图。

**做法**：在 `internal/observability` 下加了三个正交的模块，都不改动业务层：

1. **审计 `audit.go`**——环形缓冲（默认 256 条）记录危险操作（drain/shutdown/repartition），每条含时间（RFC3339）、来源 IP、操作名、参数、结果。为什么不用 slog：slog 是给运维看运行日志的，格式随级别漂移；审计是给"追溯"用的，字段必须稳定、可查询。`/admin/audit` 返回 JSON，支持 `?limit=N`。
2. **RBAC `rbac.go`**——token 换角色（readonly/operator/admin），中间件按「路径 + 方法」判定所需角色。读接口要只读，写接口（drain/shutdown/repartition）要运维，探针（healthz/readyz）永远免鉴权（否则负载均衡器会把它判死）。**默认安全姿态**：没配 token 时全开放（本地开发不被卡住），配了 token 就锁。扩展点留在 `TokenStore` 接口上，要接 LDAP/SSO 换实现即可，中间件不动。
3. **拓扑热力图 `topo.go`**——`/admin/topo` 渲染一张 SVG，把 `world.Chunks()` 的归属 + 负载画成彩色格子：负载分三档着色（0-60 绿、60-85 黄、85-100 红），主人不可达的格子画灰，本进程承载的格子描实线、远端描虚线。

**关键取舍**：热力图数据经 `OnTopo(func() any)` 回调传入，`observability` 用本地结构体（JSON 标签对齐 `world.ChunkInfo`）接收——因为 `world` import `observability`，反向 import 会成环。两个包在"字段名"这个契约上解耦，换数据源只改回调。

**实测**（单节点 2x2 分区 + `-admin-token`）：

| 验证点 | 结果 |
|---|---|
| 无 token 读 `/admin/state` | 403 |
| 无 token 写 `/admin/drain` | 403 |
| 带 token 读 | 200 |
| 探针 `/healthz` | 200（免鉴权） |
| 触发重分区后查 `/admin/audit` | 记录完整：`time`/`actor=127.0.0.1`/`action=repartition`/`detail=scene=3 to=n1`/`result=accepted` |
| `/admin/topo` | 4 个场景格子 S1-S4，每格标场景号 + 实体数（20 只怪），热力色 + 不可达灰正确 |

**踩坑**：

- **`crypto/subtle` 是伪需求**：一开始想给 token 比较加常量时间比较，但 token 存 map、按 key 查表，根本没有字符串比较这一步。常量时间比较是针对"密码哈希"这种要逐字节比的场景，map 查找不是。删掉了死代码——加安全措施前先想清楚攻击面在哪，别为了"看起来安全"堆无用功。
- **curl 在本机 Windows bash 里不可用**：之前几轮实测里 curl 一直返回空，误以为是服务端问题。实测统一走 PowerShell 的 `Invoke-WebRequest`。这不是代码 bug，是环境认知——记下来避免下一轮再踩。

### 6.18 战斗扩展：技能树 + 连招 + 驱散 + 暴击 + 护盾（M4.5 实测）

**问题**：M4 的战斗只有 3 技能 4 Buff，是"能打怪"的最小闭环。进阶机制（技能树、连招、驱散、暴击、护盾）都缺，战斗深度上不去。

**做法**：纯 combat 包内扩展，不动协议语义（只给 `CombatHit` 加一个 `Crit bool` 标志）：

1. **技能树**——`Skill` 加 `Requires`（前置技能）+ `Level`（解锁等级），`Combat` 加 `Learned` 位图。基础技能（1/2/3，无前置）天生会；技能树技能（4/5/6，带前置）要显式解锁。新增连击（普攻→连击）、处决（重击→处决）、净化之刃（驱散）三个技能。
2. **连招**——`Combat` 加 `LastSkill`/`LastCast`（只记"上一次"，不记整条链，因为当前只有两段式 A→B）。本次技能 `ComboFrom == LastSkill` 且窗口内，伤害 ×`ComboScale`。
3. **驱散**——`Skill.Dispel` 命中后移除目标所有 Buff。
4. **暴击**——`Combat.CritRate`/`CritMult`，伤害结算时按概率暴击。默认玩家暴击率 0（暴击是进阶属性），这让测试确定性。
5. **元素护盾**——`BuffShield` 先于血量吸收伤害，吸满即破。

**关键取舍**：
- **默认暴击率 0**——一开始给玩家 15% 暴击，结果原有三个测试因为随机触发暴击而 flaky（期望 220 实际 330）。暴击是"通过装备/Buff 获得"的进阶属性，默认 0 既合理又让测试确定。
- **连招只记一段**——记整条连招历史是过度设计，两段式连招只需"上一个技能 + 时间"。
- **codec 升级 v2**——`Combat.CDs` 从 `[4]` 扩到 `[8]`，新增暴击/连招/学习位图字段，存档格式加版本号，旧档兼容处理。

**实测**：新增 7 个单元测试（技能树前置、连招加成、驱散、必暴击×2、护盾吸收、codec 往返），全绿；原有 9 个测试无回归。

### 6.19 拓扑对账改增量摘要

**问题**：对账每次互换整份拓扑视图，消息量 O(N·S)（节点数 × 场景数）。个位数节点无所谓，但上百节点、上千场景时，每 2 秒一轮的全量摘要会吃掉本可给实体迁移的带宽。

**做法**：`SendTopoDigest` 拆两条路径：
- **周期广播**（`nodes` 为空）走**增量**：`World` 加 `digestSent map[uint32]uint64` 水位，只发"版本号变过或从未发过"的 Entry。稳态下（无重分区）返回空切片，一次广播 O(1)。
- **定向推送**（`nodes` 非空，节点回归/回推旧节点）走**全量**：目标节点可能漏收很多，必须给整份视图。

**为什么增量不需要全量兜底**：对账规则本身是"版本号谁高谁赢"，版本号单调递增永不回退。接收方对"没提到的场景"保持现状（本来就没变），最终一致由规则保证，不依赖每次发全量。唯一要补的是"对端完全不知道某块地"（配置漂移）——增量用"从未发过（!seen）"兜住，新地一定会被发一次。

**踩坑**：
- **新场景 ver=0 的边界**：如果只按 `ver != 上次水位` 判断，新场景（ver 恰好是 0）会被误判为"没变"而漏发。判断条件必须是"从未发过 **或** 版本变了"，二者取或。专门写了个 `TestIncrementalDigestNewSceneAlwaysSent` 钉住。

### 6.20 玩家档案落库（M5.5 实测）

**问题**：M5 的存档只存"世界状态"（怪物、拓扑版本），玩家属性（血量、等级、技能）一掉线就丢，跨进程/跨区重连回默认值。

**做法**：新建 `internal/persist` + `internal/game/player` 两个包：

1. **`persist`**——`Store` 接口（Get/Put/Delete，值用 `[]byte` 让 Store 不知道档案字段）+ `MemoryStore`（进程内 map）+ `FileStore`（每玩家一个 JSON 文件，tmp+rename 原子写）+ `RedisStore`（M6.11，key 前缀 + 可选 TTL，多节点共享同一份档案）+ `MySQLStore`（M10，最终档案）+ `LayeredStore`（M10，缓存叠最终层）。接别的数据库仍只换实现，详见 6.27。
2. **`player`**——`EnablePlayerSave(sc, store)` 挂两个钩子：进场 `load`（从 Store 读档案覆盖默认值）、离场 `save`（读 creature 属性 + combat 战斗写 Store）。放在独立包是因为它同时依赖 creature 和 combat，而 combat 反依赖 creature——放哪边都成环。

**关键取舍**：
- **档案 JSON、world 存档二进制**：玩家档案是低频、跨系统的，可读性优先（运维能 cat 文件看血量）；world 存档是高频、进程内部的，紧凑优先。两种格式各有其用。
- **离场钩子早就埋好了**：`OnEntityLeave` 从 M2 就有，`detach` 里也调了 `fireLeave`，但之前没有任何玩法包用——M5.5 是第一个消费它的。这印证了"钩子预留、玩法后补"的分层收益。
- **落库失败静默**：存档是尽力而为，玩家不会因为存储抖动被卡在离场。

**实测**：3 个 bot 连接 5 秒断开，`run/m55/players/` 生成 `bot-0/1/2.json` 三个档案（HP=1000、Level=1、Attack=120、Learned=bit1 普攻）。单元测试验证了"改血量→落库→重连恢复 HP=300 Level=7"和"战斗数据（暴击/技能解锁）随档案走"。

### 6.21 升级系统：击杀经验 → 等级 → 属性成长 + 技能门槛（M6.7）

**问题**：M4.5 引入了 `Skill.Level` 等级门槛，但玩家等级恒为 1（`creature.Attributes.Level` 出生就是 1，从没变过），导致"处决"（skill 5，Level=2）这类技能永远放不出来——等级门槛是死代码。

**做法**：打通"打怪升级"闭环，改动跨 creature + combat 两个包：

1. **`creature.Attributes` 加 `XP` 字段**（int32，等级的伴生字段）。transfer codec 从 v2 升到 v3（属性段 18→22 字节，Brain 段整体后移 4 字节），`Decode` 按版本号区分偏移，旧 v2 档仍能还原。
2. **`combat/level.go`**：升级逻辑。击杀（`dealDamage` 里 `killed` 分支）时若攻击方是玩家，给 `xpForKill=10` 经验；经验累积到 `xpToLevel(level)=level*20` 阈值就升级——清 XP、等级 +1、`applyLevelUp` 提升属性（MaxHP +100 回满血、攻击 +10），封顶 `maxLevel=20`。
3. **`skillAvailable` 接入玩家实时等级**：`sk.Level > 0 && level < sk.Level` 拒绝。这样"等级"和"技能树"解耦——等级决定"够不够格"，Learned 位图决定"会不会"。

**关键取舍**：
- **XP 放 creature、升级逻辑放 combat**：XP 是等级的伴生字段（等级在 creature），升级的触发点（击杀）在 combat，且 combat 已经 import creature。两个包不互相依赖，无环。
- **升级不改 Learned 位图**：等级到门槛 ≠ 自动学会技能，技能解锁仍由外部系统显式授予（打技能书/任务）。等级只是"能不能用"的前置，不是"会不会"的来源。

**实测**：`level_test.go` 5 个测试——击杀给经验、经验累积升级（3 杀升 2 级剩 10 XP、MaxHP+100、攻击+10）、等级门槛（1 级放不出处决、2 级能放）、等级封顶、creature v3 往返（含 XP + Brain 段偏移正确）。

### 6.22 玩家档案周期回写 + M7 压测（5000 人长稳）

**问题一：档案只在离场落库**。在线玩了一小时的玩家，进程崩溃就丢一小时的属性变化——离场是"精确的最后一笔"，但兜不住"进程随时可能挂"。

**做法**：`player.EnablePeriodicSave(sc, store, interval)` 挂一个 `StageLogic` 周期系统，用时间闸门（默认 10s）批量扫描本场景所有在线玩家落库。与离场落库互补：离场是精确兜底，周期是崩溃兜底，把丢失窗口压到 interval 以内。**为什么周期扫描而不是"变化即写"**：属性每帧都可能变，同步落盘（FileStore 是 tmp+rename 两次 IO）会拖垮 tick 协程，周期批量把 N 次变化合并成一次 IO。

**问题二：单 World 能扛多少人**（M7）。补战斗结算 benchmark + 实测 5000 怪单进程。

**实测（5000 怪单进程，i5-7500）**：
- **完整帧 1.27ms**（含战斗 Buff tick + AI + 回血 + 同步），占 50ms 帧预算的 2.5%；稳态帧（低频系统闸门关闭）更低。
- **单次伤害结算 380ns、完整攻击 594ns**——攻击是战斗链路最频繁的操作，微秒级以下完全扛得住高频攻击。
- **wander AI 是最大单点**（4ms），但 < 8% 预算，可接受。
- **内存 6.1MB / 5000 实体**、8 goroutine、tickLag 133µs——单写者模型 + 稀疏集把开销压到极低。
- 指标大盘（`/metrics` 70 行）完整反映规模：`scene_entity_count=5000`、`scene_tick_duration_nanoseconds=1.98ms`、ID 账目平（5000 分配 / 5000 live / 0 冷却）。

**结论**：单 World 5000 人毫无压力，瓶颈在未来（主城密度、跨进程迁移吞吐），不在单进程算力。

### 6.23 控制台 SSE 增量推送（M6.10）

**问题**：控制台 1.5s 轮询 `/api/overview`，`setInterval` 有固有缺点——客户端计时漂移、断线后仍空转请求、多个标签页各自轮询浪费。架构图里原计划上 WebSocket。

**做法**：改用 **SSE（Server-Sent Events）**，`control/api.go` 加 `handleStream`：
- 抽 `buildOverview()`，让轮询响应和 SSE 推送共用同一份组装逻辑（两个通道数据结构必须一致，否则前端切换数据源时字段缺失）。
- `/api/stream` 用 `http.Flusher` 推 `data: <json>\n\n`，立即推首帧、之后 1.5s 一帧，`r.Context().Done()` 感知断开。
- 前端 `EventSource` 订阅，`onopen`/`onmessage`/`onerror` 分别更新连接状态灯；EventSource 自动重连，比 setInterval 健壮。

**为什么是 SSE 不是 WebSocket**：
1. **语义匹配**：控制台的实时需求是"服务端单向推状态"，没有"客户端往服务端发消息"（写操作走 POST）。WebSocket 的双向对控制台是多余的。
2. **零依赖是硬约束**：项目 go.mod 零 require。SSE 是纯 HTTP 长连接，标准库就能实现；手写 WebSocket（RFC 6455 握手 + 帧编解码 + 掩码 + 关闭握手）会引入一大块易出错的代码，收益却只有"控制台能推消息"。

**实测**：`stream_test.go` 2 个测试——SSE 内容类型 + 首帧立即推 + 数据可解析；buildOverview 一致性。端到端启动 control.exe，`/api/stream` 返回 `text/event-stream`、首帧完整 overview JSON、空行边界正确。

### 6.24 玩家档案接 Redis（M6.11）

**问题**：M5.5 的 `FileStore` 每节点各存一份档案，跨节点恢复要靠共享盘；M6.8 的周期回写也只在本节点生效。多节点部署时玩家在 A 节点下线、B 节点重连拿不回血量等级。

**做法**：给 `persist.Store` 加第三个后端 `RedisStore`（`persist/redis.go`），业务层零改动——`player` 包只认 `Store` 接口。

1. **`RedisStore`**：`NewRedisStore(addr, password, db, prefix)` 构造时 `Ping` 一次（3s 超时），连不上直接报错——持久化后端必须在启动时可用，不能运行期才发现。键 `<prefix><player>`（默认 `player:`），可选 TTL。`Get` 里 `redis.Nil` 和网络错误都归为"没读到"（返回 false），档案是尽力而为的兜底，Redis 抖动不该拒绝玩家进场。
2. **接入 `cmd/server`**：`-redis-addr`/`-redis-password`/`-redis-db`/`-redis-prefix` 参数，优先级 Redis > 文件目录 > 不落。优雅退出用一个极简 `redisComponent` 包装 `Close()`，挂在 `gate` 之前注册（逆序停止时在网关停之后、场景停之前释放连接）。

**关键取舍**：
- **引入 `go-redis/v9` 打破了"零外部依赖"**。这是项目第一个外部依赖，值得专门说：Redis 客户端手写 RESP 协议（像 SSE 那样）收益极低——RESP 有 5 种数据类型、连接池、重连、Cluster 等一堆工程细节，手写容易出 bug 还修不完。零依赖的价值在于"核心路径（协议、ECS、AOI、拓扑）可审计、无黑盒"，玩家档案这种外围持久化引入一个成熟客户端是划算的。**但版本要盯住**：`go-redis` 最新版要求 go 1.26，会触发 toolchain 自动升级；本项目钉在 `v9.16.0`（要求 go 1.18，兼容本机 go 1.23.1），避免无意中升级编译器。
- **Redis 是"在线缓存"不是"最终档案"**：蓝图里三层存储是「内存 → Redis → MySQL」，Redis 这层在 M6.11 补上；最终档案层（MySQL）与两层叠合的 `LayeredStore` 在 **M10** 落地，见 6.27。

**实测**：`redis_test.go` 3 个测试——读写删、前缀隔离、连不上报错（用环境变量 `REDIS_ADDR` 控制，没 Redis 自动 skip）。端到端：server 配 `-redis-addr 127.0.0.1:6379` 启动，3 个 bot 连接 4 秒断开，Redis 里出现 `player:bot-0/1/2` 三个键，`GET player:bot-0` 返回完整档案（含 M6.7 的 xp/critRate/critMult/learned 字段）。

### 6.25 Godot 客户端框架（M8）

**问题**：服务端协议、拓扑、战斗、存档、控制面都齐了，但没有客户端验证"这堆协议真能跑起来"——协议层的字节格式、HMAC 登录、进场景、移动、攻击、心跳，到底对不对只有 `tools/bot`（Go 版）在验证。需要一个独立的、异语言实现来交叉验证协议正确性，同时给出可扩展的 2D 客户端骨架。

**做法**：用 **Godot 4.7.2**（引擎在 `E:/install/gobot/`）做一个 2D 俯视角客户端，工程在 `client/godot/`。分层和 Go 端一一对应：

1. **协议层（纯算法、零依赖、可单测）**：`ow_writer/ow_reader`（大端，对齐 `internal/protocol/buf.go`）、`ow_proto`（消息 ID + 帧打包/解包，对齐 `protocol.go`/`frame.go`）、`ow_auth`（HMAC-SHA256 token，对齐 `pkg/authtoken`）、`ow_messages`（15 条消息 Encode/Decode，对齐 `protocol/messages.go`）。
2. **网络层 `ow_net_client.gd`**：`StreamPeerTCP` 连接 + `_process` 轮询收帧 + 状态机（CONNECTING→LOGGING_IN→ENTERING→READY→CLOSED）+ 信号解耦（`connected/login_ok/entered/entity_enter/entity_state/entity_leave/entity_attr/combat_hit/kicked/notice/rtt_ms/disconnected`）。时序精确复刻 `tools/bot`：TCP → Login(token) → LoginResp → EnterScene(空) → EnterSceneResp → 就绪 → 移动/心跳/攻击。
3. **表现层**：`world_view`（实体增删改、血条、伤害飘字、摄像机跟随）、`entity_node`（单体色块+血条）、`hud`（调试信息）、`main`（组装 + WASD/点击输入 + 配置）。服务端权威 + 客户端预测（移动每 100ms 上报意图、本地先插值、EntityState 回来纠正）。
4. **自测**：`probe.gd`（引擎 API 探针）、`protocol_test.gd`（Go 端生成"黄金字节"硬编码进测试，解码断言字段 + 编码回 hex 比对，逐字节验证）、`integration_test.gd`（连真实 server 走完整链路）。

**关键取舍**：
- **用 Godot 而非裸 OpenGL/SDL**：框架阶段要的是"快速验证协议 + 可扩展的渲染骨架"，Godot 的 `StreamPeerTCP`/`StreamPeerBuffer`/`HMACContext` 让二进制协议对接几乎零样板，省下写渲染/输入系统的功夫。坐标是服务端 3D 但玩法只用 x/z 平面，客户端按 2D 渲染（(x,z)→(x,y)），要真 3D 只换 `world_view` 的 `Node2D` 为 `Node3D`，协议层不动。
- **协议字节级交叉验证**：不靠"看起来能连上"，而是 Go 端生成黄金字节、Godot 端逐字段断言。这一步抓出了"GDScript `StreamPeerBuffer.big_endian` 与 Go `binary.BigEndian` 完全一致"和"HMAC 结果 `adeeb955...` 完全一致"两件关键事实——没有它，异语言客户端的协议对齐只能靠肉眼比对。
- **网络层用信号而非回调**：`main.gd` 只接信号不碰 socket，表现层可独立替换（`entity_node` 从 `ColorRect` 换成 `Sprite2D` 即可上美术），协议/网络层不动。

**实测**：
- 协议层 `protocol_test.gd` 54 个断言全绿（含中文 UTF-8、负数字段、token HMAC、Go 黄金字节解码、编码回 hex 比对）。
- 集成 `integration_test.gd` 8 项全绿：TCP 连上 → Go 服务端接受 Godot 签发的 HMAC token → 进场景拿 entity_id → 收到 53 个实体广播（朝怪群中心移动时）→ 发 MoveReq 不踢 → 心跳 RTT 7ms → 结束仍 READY。
- 图形主场景 `--ow-verify` 模式：真实数据流下 state=READY、self_node 已建、信号链全通（VERIFY_RESULT=PASS）。

### 6.26 客户端玩法 UI：技能树面板 + 小地图（M9）

**问题**：M8 只验证了"协议能跑通"，表现层是纯调试 HUD（血量/等级/坐标）+ 硬编码的 3 个技能名。客户端还没把服务端的**玩法数据**呈现出来——玩家看不到自己会什么技能、技能之间怎么解锁、周围有什么。

**做法**：分成"协议"和"表现"两层，协议层沿用 M8 的字节级交叉验证思路。

1. **技能目录协议（新增 2 条消息）**：`C2S_QUERY_SKILLS(0x0010)` 空包上行，`S2C_SKILL_LIST(0x0011)` 下行 `SkillList{ Skills[]SkillInfo, Learned uint64 }`。`SkillInfo` 逐字段对齐 `combat.Skill`（ID/Name/Damage/Range/CooldownMs/AOE/AOERad/Level/Requires/ComboFrom/ComboScale/Dispel），`Learned` 是已解锁位图。
   - **下发包必须走场景 goroutine**（单写者规则的延伸）：Gate 收到查询后像攻击一样转发语义给实体所在场景（`Scene.QuerySkills` → mailbox），由 `combat` 注入的 `querySkills` 处理器在 tick 协程里读实体 `Combat.Learned`、现编目录、经 `Scene.SendTo(entity, ...)` 回包。**绝不在 Gate goroutine 直接读实体战斗组件**——那会和无锁的单写者并发。
   - 跨节点同理：`mesh.RelaySkills` 把查询投到实体所在节点的场景，那边本地处理；对端路径与 `RelayAttack` 对称。
2. **技能树面板 `skill_tree.gd`（CanvasLayer）**：收到 `skill_list` 信号后按目录重建按钮列表，可用性判定**逐字段镜像服务端 `combat.skillAvailable`**（基础技能恒可用；技能树技能需等级达标 + 前置已学 + 自身已学）。三态着色（绿=可用/黄=已学但等级不足/灰=锁定），点击可用技能经 `skill_selected` 信号切换当前施法技能，HUD 同步。
3. **小地图 `minimap.gd`（CanvasLayer）**：每 4Hz 把 `world.entities` 以"自己为中心"重投影成相对点（服务端已在广播 EntityState，客户端本地投影即可，不另开协议）。自己恒在中心，其他实体按相对坐标缩放后画点，超出半径裁剪。

**关键取舍**：
- **目录进程级共享、现编不缓存**：技能表极少变化，每次查询现编成本可忽略，省去"表变了要失效缓存"的麻烦；玩家只关心 `Learned` 位图。
- **可用性客户端算、服务端再校验**：客户端灰掉不可用的技能是体验，服务端攻击时仍会按 `skillAvailable` 拒绝——两侧逻辑同源（同一套字段），不会出现"客户端能点但服务端报错"的错位。
- **小地图不新增协议**：直接复用 EntityState 广播，避免为"客户端想看旁边有谁"多一趟下行。

**实测**：
- 协议层 `protocol_test.gd` 新增 `S2C_SKILL_LIST` 黄金字节解码（目录 2 技能 + learned 位图）+ `C2S_QUERY_SKILLS` 空包断言，全项目 76 个断言全绿（含 Go 端生成黄金字节、GDScript 逐字段解码一致）。
- Go 端 `messages_test.go` 新增 `SkillList` 往返 + 截断拒绝测试，全绿。
- 集成 `integration_test.gd` 升级为 9 项：连真服务端后进场发 `C2S_QUERY_SKILLS`，收到 `skill_list catalog=6 learned=2`（6 个技能、默认解锁普攻），断言通过。
- 图形主场景 `--ow-verify` 模式新增 `skill_catalog`/`skill_list_ok` 校验：真实数据流下 `VERIFY skill_catalog=6 skill_list_ok=true`，`VERIFY_RESULT=PASS`——证明 `skill_tree.gd` 重建与 `minimap.gd` 绘制在真实场景里不崩。

> 背包（Inventory）本期**未做**：服务端目前没有物品/背包系统，"技能树/背包/地图"三件套里只有技能树和地图有服务端数据支撑；等 `creature`/`combat` 接入物品系统后，再按同样"协议 + 面板"两步走。

### 6.27 玩家档案接 MySQL：最终档案 + 在线缓存分层（M10）

**问题**：M6.11 结尾留了一句话——"Redis 是在线缓存不是最终档案，最终档案（MySQL/其他数据库）仍是下一步"。档案此前只有 `MemoryStore`（进程内）、`FileStore`（每节点一份文件）、`RedisStore`（多节点共享但可能被淘汰/设 TTL/被 flush）三种后端，都撑不起"权威、持久、崩溃与清缓存之后仍在"的真相层。

**做法**：把蓝图里的「内存 → Redis → MySQL」补齐，但**不是再加一个平级后端**，而是让 MySQL 和 Redis 叠起来各司其职。业务层（`game/player`）依旧只认 `persist.Store`，零改动。

1. **`MySQLStore`（`persist/mysql.go`）**：实现 `Store`。构造时 `Ping`（5s 超时）+ `CREATE TABLE IF NOT EXISTS player_records`（`player VARCHAR(191)` 主键、`data MEDIUMBLOB`、`updated_at BIGINT`），连不上或建表失败直接让进程启动失败——持久化后端不能等运行期才发现不可用。`Put` 用 `INSERT ... ON DUPLICATE KEY UPDATE` 保证反复落库幂等；`Get` 里没这一行或任何错误都返回 `(nil, false)`，和 `RedisStore` 一致：读不到档案是"新玩家第一次登录"的常态，MySQL 抖动不该让玩家进不了场。`data` 用 `MEDIUMBLOB` 而非 `TEXT`，避免 MySQL 做字符集转换把 JSON 字节改坏。
2. **`LayeredStore`（`persist/layered.go`）**：两个 `Store` 组合成一层，`cache`（Redis）+ `final`（MySQL）。`Get` 先查缓存，未命中查最终层并**回填缓存**；`Put` 先写最终层再写缓存；`Delete` 两层都删（缓存删失败不影响真相，忽略）；`Close` 逐层判断 `Closer` 后释放。
3. **`Closer` 接口（`persist/store.go`）**：把"需要释放连接池"从具体类型抽成接口。`cmd/server` 原来按 `if _, ok := playerStore.(*persist.RedisStore)` 注册 `redisComponent`——换成 MySQL 或 Layered 之后这个断言会**静默失效**，连接不显式关也能跑，直到压测时才怀疑连接池泄漏。改成按 `persist.Closer` 断言注册通用的 `playerStoreComponent`，不管底层是 `RedisStore` / `MySQLStore` / `LayeredStore` 都统一收口。
4. **`-mysql-dsn` 接入**：优先级 `MySQL+Redis → LayeredStore` > 仅 MySQL > 仅 Redis > 文件目录 > 不落。两者都配时日志打 `player records on mysql (final) + redis (cache)`。

**关键取舍**：
- **写顺序是 final 先、cache 后，这不是风格问题**。最终层是真相、缓存是派生：先写最终层失败就直接返回错误、缓存根本不动（下次读 miss 再回填即可）；反过来若先写缓存、最终层写失败，会留下"缓存有新数据、真相还是旧的"的脏读，而且它会一直存在到下一次成功写入。读回填里的 `cache.Put` 错误也刻意忽略——缓存是加速，不是正确性依赖。
- **不引入 ORM、不引入迁移框架**。`Store` 的值就是 `[]byte`（Store 不该知道档案有哪些字段），SQL 手写到 `database/sql` 一层足够；ORM 会把这层抽象冲掉。表在构造时自建，部署和单测都能直接跑，代价是没有 schema 版本管理——字段真要演进时得自己 `ALTER`，当前结构稳定够用。
- **换后端不动 IO 路径**。落库仍然走 M5.5 的 `OnEntityLeave` 钩子 + M6.8 的周期批量回写（StageLogic 时间闸门），这两条都在 tick 外/低频路径上，符合"tick 里不做 IO"。没有因为接了数据库就把 `Put` 塞进每帧。
- **第二个外部依赖，同样钉版本**：`github.com/go-sql-driver/mysql v1.8.1`（要求 go 1.18）。和 `go-redis v9.16.0` 一个理由——最新版会要求更高的 go 版本并触发 toolchain 自动升级，本机是 go 1.23.1，所有 Go 命令继续带 `GOTOOLCHAIN=local`。

**实测**：
- 单测：`mysql_test.go` 3 个（往返删 / upsert 幂等 / 连不上报错，`MYSQL_DSN` 控制，无 MySQL 自动 skip 并尝试自举建库）、`layered_test.go` 5 个（写双落 / 读回填 / 删双删 / 两层都空 / `Close` 透传）、`layered_integration_test.go` 1 个（**真实 MySQL + Redis**，模拟缓存逐出后从最终层回填，任一服务不可用自动 skip）。全量 `go test ./...` 全绿。
- 端到端：server 配 `-mysql-dsn + -redis-addr` 启动，2 个 bot 登录 8s 后断开 → MySQL `player_records` 出现 `bot-0/bot-1`（191 字节完整档案），Redis `m10:bot-0/1` 同步出现，两层内容一致（`E2E_RESULT=PASS`）。
- 进场恢复：手工把 MySQL 里 `bot-0` 改成 `hp=555 / level=9`、删掉它的 Redis key，再让 `bot-0` 重连 → 两层都变成 `hp=555 / level=9`。这条同时证明了缓存逐出后 `Get` 从最终层读回、回填缓存、属性被恢复三件事在真实服务端里都发生了。
- 优雅关服：`POST /admin/shutdown` → 日志 `component stopped component=player-store`，exit 0，连接池正常释放。

## 十、几个容易踩的坑

1. **别过早微服务化**。一开始 Gate 和 World 放一个进程也能跑，先跑通逻辑再拆，拆的时候接口已经清晰了。
2. **别给每个实体开 goroutine**。这是 Go 写游戏服务端最容易犯的错，3 万实体就是 3 万个 goroutine 争抢调度。
3. **别在 tick 里做 IO**。落盘、RPC、Redis 全部异步化，tick 里只做纯内存计算。
4. **别用 `time.After` 做游戏计时**。每次调用都创建一个 timer，几万个就爆了。用帧号驱动的 Scheduler。
5. **别让客户端权威**。位置、伤害、掉落，全部服务端算，客户端只做表现。
6. **AOI 一定要压测**。这是唯一一个"逻辑对但性能错"就完全不可用的模块。
7. **控制面别和数据面同生共死**。控制台若部署在业务进程里，进程挂了就看不了状态、也没法重启它——等于失去了一半价值。控制面要独立部署、独立数据库。
8. **开关服接口别做成同步阻塞**。一次开服要跑两分钟，同步接口会超时、会重试、会重复开服。一律异步任务 + taskId + 幂等键。
9. **状态判定别只信 HTTP 探活**。进程被 OOM kill 时 HTTP 直接不通，但网络分区也会不通，两种情况处理方式完全不同。以 etcd lease 为准，探活只作细节补充。
10. **tick 和消息不要写成两个平行的 select 分支**。`select { case <-ticker.C: tick(); case m := <-mailbox: handle(m) }` 在 mailbox 持续非空时，两个 case 都会被随机选中，ticker 的帧会被丢掉。实测 500 人在线时累积出 **250ms 的 tick 滞后**。正确写法：只在 tick 分支里批量 drain mailbox，并限制单帧处理上限。
11. **虚拟化环境的时钟精度可能差到测不出微秒**。本机实测 `1000 次 time.Now()` 差值为 0 ns，单帧几微秒的 CPU 耗时会一律测成 0。tick 健康度要看**相邻帧间隔偏差**（基于 50ms 量级），不要看单帧耗时，也不要看"实际时刻 - 理想时刻"的相位偏移（启动卡一次就会永久显示大数字）。
12. **高频状态输入不要用消息队列**。移动、朝向、按键这类"只关心最新值"的输入，一旦走队列就会出现"同一帧处理同一个实体的 5 个版本"，而且客户端发得越快服务端压力越大——作弊客户端一个人就能把 tick 打满。用覆盖式缓冲后，每帧工作量以实体数为上界，与发包频率无关。
13. **配置文件里可能藏着 BOM**。Windows 上的编辑器和 `Set-Content -Encoding utf8` 都会写 UTF-8 BOM，而 `encoding/json` 遇到 BOM 直接报 `invalid character 'ï'`。表现是"重启后状态全丢"且只有一行 warn。读任何 json 配置前先 `bytes.TrimPrefix(b, []byte{0xEF,0xBB,0xBF})`。
14. **前端按钮的 disabled 会被覆盖**。用 JS 统一刷新按钮状态时，`el.disabled = busy` 会把服务端渲染时的禁用判断一起擦掉，结果是"运行中的区服还能再点一次开服"。要么把语义禁用和临时忙合并成一个判断，要么根本不要在刷新时碰 disabled。
15. **benchmark 的两个经典陷阱**。空实现的接口会让编码结果被栈分配（`0 allocs` 是假的，要用 sink 强制逃逸）；只进不出的循环会让被测对象随 `b.N` 膨胀（`BenchmarkEnter` 曾测出 105µs，改成进出配对后是 3µs）。
16. **NPC 的广播出口是空实现，但调用不是免费的**。给每只怪都塞一个 `nopClient` 能让广播路径没有 nil 分支，可一旦怪物密集（3×3 相邻全是怪），一半以上的广播收件人是另一只怪——编码、接口调用全白做。广播循环里必须过滤 `kind != KindPlayer`，实测 2000 怪场景广播量从 550k/s 降到 79k/s。
17. **实体离场只摘索引不广播，会留下"幽灵"**。早期心跳超时踢人时只做了 `grid.Remove` + `delete(entities)`，没发 `EntityLeave`，表现是"挂机的人在你眼里一直站着不动"。离场必须走同一个出口（`removeEntity`：回调 → 广播 → 摘索引 → 清组件），四步一个都不能少。
18. **稀疏集遍历时增删同一个池，会跳过元素**。swap-remove 把末尾元素搬到当前位置，如果末尾还没遍历到，它就被跳过了。要边遍历边删，先取 `IDs()` 快照。
19. **本机 `time.Now()` 的粒度是 1.00ms**（实测 20 万次相邻差值全是 0 或 1.0024ms）。后果：`/admin/state` 里的 `lastTickNs` 和每个 System 的 `lastNs` 只能是 0 或 1ms 两档，**不能用来做微秒级调优**——那些数字要看 `go test -bench`（走 runtime 的纳秒计时）。线上健康度只看 tick 滞后，它是 50ms 量级，1ms 粒度带来的误差可以忽略。
20. **`s = s[n:]` 之后 `append` 会重新分配**。切片前移不回收容量：`cap` 剩多少就只能 append 多少，用完之后每次 append 都要 make 一个新数组。ID 冷却队列最初就是这么写的，复用路径实测 295 ns/op + 32 B/op——比分配新号还慢 8 倍，而且看起来"只是挪了个指针"。队列类结构要么用游标 + 摊还压缩，要么用环形缓冲，别用切片前移。
21. **复用一个 ID 之前，先想清楚"在途的包"**。往任何被缓存的句柄（实体 ID、会话 ID、请求序号）上做回收，都要先给出一个"多久之后旧引用不可能再出现"的界，然后用它做冷却。没有这个界就直接复用，等于把一个必然发生的竞态藏进了"很少触发"里。
22. **分层存储的写顺序反了会留下永久脏读**。缓存 + 最终层的 `Put` 必须**先写最终层、后写缓存**：先写真相失败就直接返回，缓存不动，下次读 miss 再回填；若先写缓存而真相写失败，"缓存有新值、真相是旧值"会一直存在到下一次成功写入。读回填里的缓存写失败则要忽略——缓存是加速不是正确性依赖。
23. **优雅退出的关闭注册别按具体类型断言**。`if _, ok := store.(*persist.RedisStore)` 在换成 MySQL 或叠成 `LayeredStore` 之后会**静默失效**：进程照常跑、连接不显式关，直到压测才怀疑连接池泄漏。抽一个 `Closer` 接口按能力断言，新增后端不用回来改这段。
24. **"没归档"和"读失败"必须走同一条路**。`Get` 里查无此行与 MySQL/Redis 报错都返回 `(nil, false)`，用默认属性进场。把后端抖动当异常抛出去，等于数据库一抖就拒绝所有新玩家登录——而新玩家本来就没有档案。
