## 单场景容量基线（回答"实体上限是多少"）

- 代码无实体数硬上限，但 `maxMsgsPerTick=4096` 是真正的天花板：10Hz 移动下 8192 实体即打满每帧配额，之后是输入延迟累积 → 邮箱（8192）丢包。所以当前安全线约 8000 实体，与机器性能无关。
- 新增 `internal/world/scene_bench_test.go`（BenchmarkMoveBroadcast / BenchmarkEnter），单核实测 i5-7500：
  - 2000 人散落 1000m（~2 人/格）：1.38 µs/条 → 单核约 2.9 万实体
  - 2000 人集中 300m（~22 人/格）：4.51 µs/条 → 约 8800 实体
  - 2000 人挤 100m 主城（~205 人/格）：67.5 µs/条 → **约 590 实体**
  - 同一份代码差 49 倍。广播成本 O(邻域人数)，邻域人数随密度平方增长。
- 结论：上限不由总人数决定，由**每格人数**决定。这是 M2 必须做正式 AOI + 主城分线的直接依据。
- 压测对照实验：2000 bot 低频移动（-move 1s）时 tick 滞后 ≈ 0、server CPU 18.6%、bot CPU 71%；同数量高频（-move 100ms）时滞后 232ms。判定为**压测机 CPU 争抢**（bot 打满）而非服务端算不过来——同机压测结果会低估服务端能力，需注明。
- 已把上述内容写进 ARCHITECTURE.md 6.4 节。

## M2：AOI 空间索引（已完成）

- 新增 `internal/aoi`（泛型 `Grid[T]`），三条设计原则：格子内用 slice（swap-remove 保持 O(1) 删除）；格子尺寸与视野半径解耦（`WithAOI(cellSize, radius)`）；差集查询不建临时集合（遍历新视野 + `InView` 判断旧视野）。

- 测试：aoi 包 7 个用例，含 3000 步随机操作的性质测试（索引结果必须与暴力过滤完全一致）；world 包新增跨格视野差集测试、索引与 e.cell 同步测试。全绿。
- 基准（i5-7500 单核，单条移动含广播）：散落 2000 人 457ns（原 1.42µs，3.1×）、集中 300m 1.07µs（5.0×）、主城 100m 5.63µs（原 54.2µs，9.6×）。
  - 提升可拆解：纯实现优化 3.4×（同 96m 视野 54.2→15.9µs），视野缩小 2.8×（15.9→5.63µs）。别混为一谈。

# M3.1 实体 ID 冷却回收

## 问题

组件池 `sparse []int32` 用实体 ID 直接下标寻址，长度 = 历史最大 ID。ID 单调递增不复用 → 长跑后每池摊着一个几 MB 全零数组，而同时在线只有几千人。

## 新增

- `internal/world/idalloc.go`：`idAlloc`（mutex 保护）。三段式 ID 空间：`next` 高水位 / `free` 可复用 LIFO 栈 / `cool` 冷却队列（2 秒，按释放时间有序）。分配先弹 free 再推 next；上限 `1<<20`（4MB/池），耗尽返回 0。`IDStat` 进 `/admin/state` 的 `ids` 字段，另有 `scene_entity_id_high_water`、`scene_entity_id_live` 两个 gauge。
- `ecs.PoolStat.Sparse`：暴露稀疏数组长度，让"组件数没变但内存在漏"可观测。
- `Scene.Spawn` 返回 nil（耗尽）、`Enter` 返回 0（耗尽或邮箱满）、Gate 回 `CodeServerBusy "scene is full"`。
- 测试：`idalloc_test.go` 7 个用例（含 8 协程并发唯一性、冷却边界、耗尽）、`idrecycle_test.go` 4 个用例（含 2 万次生灭的对照实验）。

## 关键决定

- 冷却按**时间**不按 tick：改 `-tick-ms` 不应该改安全性；2 秒 = 公网 RTT 的 5~10 倍余量。
- 分配要加锁：玩家进场走 Gate 读协程（需同步拿 ID 填会话），NPC 生成在 tick 协程。搬进 tick 会让进场等一帧并阻塞读协程。
- `removeEntity` 里 ID 最后还（早还会出现同帧两个实例同 ID）。

## 这轮踩的坑（已写进 ARCHITECTURE 第 20-21 条 + 6.7 节）

- **`cool = cool[head:]` + append 每轮一次堆分配**：切片前移不回收容量，cap 缩到 0 后 append 就 make。复用路径 295ns/32B（比分配新号还慢 8 倍）。改"游标 + 摊还压缩"→ 64ns、0 alloc。
- **游标只进不退，冷却队列自己会漏**：修完上一条后 cool 头部是死空间，若没有"队列被清空"的空闲时刻会一直涨。加摊还压缩（死空间占一半就整体前移）。
- **邮箱满时已分出去的 ID 没还**：`Enter` 先分配再投递，投递失败实体永不建出来，ID 永久漏，泄漏量正比于登录洪峰。

## 实测

- 单测对照（同一代码只改冷却）：累计 2 万次生灭、峰值 2000 → 不回收 sparse=32752（127KB/池），回收 sparse=2032（7KB/池），**16 倍**，且差距是线性的。
- 端到端（2000 怪常驻 + 6 轮各 400~500 机器人进出，共 ~2600 次）：高水位 3 轮后 2497，6 轮后仍是 **2497**（复用 2169 次）。不回收应为 4600。
- 分配：新号 37ns、复用 64ns，均 0 alloc。

## 做了什么

- `internal/net/dial.go`（新）：节点链路复用客户端 TCP 栈，`Conn.Send` 拆 `TrySend`/`Send` 两种拥塞策略。
- `internal/world/topology.go` 重写：owner 从 `*Scene` 换成 `mesh.Peer`；`Add`（本地）/`AddRemote`（只登记边界）。
- `internal/world/config.go`（新）：`configs/world-2node.json` 装载、校验、`Local/Remote` 划分、`Partition` 按节点名字典序定 offset。
- `internal/world/idalloc.go`：`next`→`seq`，`id = seq × stride + offset`；`release` 返回 foreign 让调用方通知所有者；`IDStat.Foreign/Stride/Offset`。
- `internal/world/peer.go`（新）：节点消息分发，`RelayMove` 直接 `s.Move`（不再进 mailbox，少一跳）。
- `internal/gate/peer.go`（新）：`remoteClient`（Send→ClientSend、RouteTo→Rebind）+ `sessionRoute`，Gate 侧 `Deliver`。
- `internal/world/transfer.go` / `scene.go`：`send()` 本地进 mailbox、远端才编码；`land()` 本地/远端共用；`detach()` 明确**不回收 ID**。
- `cmd/server`：`-node/-node-addr/-world`；组件顺序 mesh→scene→gate→admin。

## 关键决定

- **连接不跟着实体走，包跟着连接走**：TCP 不能跨进程搬。实体搬到哪，下行包经 `ClientSend` 回接入节点写 socket，上行 Move/Heartbeat 经 `Relay` 转发，落地后一次 `Rebind` 改路由。规则只有一条：连接在哪进来就永远在哪。
- **步长分区而非高位编号**：组件池用 ID 直接下标，高位放节点号会让每个池至少 `2^16×节点数`。
- **跨节点拥塞策略与客户端相反**：客户端队列满→断开（背压）；节点链路满→丢当前帧（否则一次拥塞会把队列里在途的 Prepare 一起蒸发）。
- **`Assign` 只在本节点场景里散列**：把跨进程限制在"走过去"一个动作上，避免"上线即跨进程"这条新路径。

## 这轮踩的坑（已写进 ARCHITECTURE 6.9 四条）

- 复用 `Conn.Send`（满即断）→ 首测 8 次 `handover aborted: timeout`、n2 `sendFail=12`，日志里连"Admit 收不到"都没有。改 `TrySend`。
- 迁移已 0 失败但 `moveRejected` 涨到 855 → 输入帧被丢导致位置错位，队列 256→4096 后归零。
- 外来 ID 不回收 = 泄漏：n1 `live` 永不下降（漏 95 个）。加 `MsgReleaseID` 才平。
- 测试里直接改 `e.SetSpeed` 与 tick 抢数据 → 加 `Scene.SetSpeed` 走 mailbox；`TestCrossNodeHandover` 一跳 400m 被速度钳制 → 改成 30ms 连发 40 次。

- **成员变化只影响可达性**：节点挂了把地块从路由摘掉，玩家被夹住；不增删场景、不改拓扑。
- etcd 适配器**没做**：本机无 etcd/docker，不想交付没在真集群跑过的客户端。接口已冻结，加实现即可。

## 关键决定

- **两种动作，代价差一个数量级**：搬迁（有人要搬，与人头成正比）/ 接管（人随进程消失，O(1)）。接管是搬迁的退化情形。
- **拓扑切换必须有先后**：目标先接（standby，能收 Commit 但不在路由里）→ 激活 → 广播 → 源摘。各改各的会双写者。
- **唯一硬规则：搬人之前可以干净回滚，开始搬之后只能往前**。Prepare 重试 3 次后中止；排空永不中止（先发后摘，失败只是这一帧停下）；Activate 无限重发。
- **排空不走 tryHandover**：那条路依赖 Route 指向对面，而重分区期间路由还指自己。直接构造 Commit，落地仍复用 `land()`。
- **限速 64/帧**：不是省 CPU，是给节点链路 4096 队列留空间。一帧 5000 个 Commit 会把队列灌满，丢掉一部分就变成"搬了一半"。
- `detach` 仍然不回收 ID（同 M3.3）：ID 属于源节点，实体在对面死掉才经 `MsgReleaseID` 归还。

## 这轮踩的坑

1. **接管方又刷了一份怪**：工厂里有"刷 100 只怪"，接管照跑，169 实体的地变成 269。加 `SceneSpec.Incoming`，`>0` 就不预填充。
2. **`Activated` 忘了置 `OK=true`**：目标已接管，发起方走进 `if !act.OK` 直接返回、**自己不改路由**。两边认知不一致，日志只有一行 `activate refused reason=""`。bool 零值恰好是错误分支的经典翻车。
3. **`NoClient` 用 `client == nil` 判断**：跨进程搬玩家时 `payload.client` 本来就该是 nil（换成了 ClientRef），结果把玩家当 NPC 落地，跳过 resolveRef → 不切路由。改成按 `kind != KindPlayer`。
4. **测试断言早了几十毫秒**：以"目标收了 N 个实体"为完成条件，此时 Activate/Activated 还没走完，源节点还没退休。应以"源节点 `Scene(id)` 消失"为准。

## 关键决定

- **版本号只在归属变化时 +1**。每次广播都 +1 会让两个节点互相"证明"自己更新，谁也不服谁。
- **同版本不同归属用确定性裁决**：两边都取 `min(owner)` 并各自 +1 → 独立算出同一结果，不需要协商、不乒乓。
  写成"谁收到谁改"会永远收敛不了。
- **广播和对账共用同一套比较规则**（`reconcileEntry` / `applyRemoteMove`），否则会出现"广播接受、对账拒绝"的僵局。
- **对账跳过 Moving/Standby 的场景**：中间态看起来正是"两边都是主人"。
- **退休必须走 tick 协程**（`msgRetire`）：直接 Stop 会连 ID 一起丢。

## 这轮踩的坑

1. **退休不回收 ID**：第一版 `Stop` 之后 `live=100 / cooling=0` 永不下降。改成 tick 里 `removeEntity` → `live=0 / cooling=100`。
2. **广播被死节点拖慢**：串行循环给已死的 n2 拨号卡 ~1s，排在后面的 n1 反而比对账晚 0.5s 收到。
   加 `NodeAlive` 过滤后不再发生（也让日志少一堆无意义 warn）。
3. **`peerAndVersion` 必须原子**：分开取 `PeerOf` 和 `nextVersion`，中间夹进别人的重分区就会"旧地址配新版本号"，
   对端会照单全收。只能一次在锁里取完。
4. **启动窗口**：重启节点按配置建场景是必然的，纠正要一次摘要往返。网关前留 300ms（`firstDigestWindow`）。

## 实测（三节点，configs/world-3node.json，每场景 100 只怪）

- 基线：三份摘要一致，`vers` 全 0，`applied=0`。
- 搬迁 n3 scene3→n1：三节点 `vers[3]=1`，n2 走广播（`applied=0`）。
- `kill -9` n2 → n3 接管 scene2（selfReclaim），n1/n3 `vers[2]=1`。
- **重启 n2**：+37ms `adopted peer view scene=2 owner=n3 ver=1` / `scene=3 owner=n1 ver=1`；
  +57ms `scene purged scene=2 entities=100`；`applied=2 retired=1`；三节点 `chunks` 一致。
- ID：n2 `live=0 cooling=100`（100 个怪 ID 全部回到冷却队列）。
- 通行：60 bot 从 n3 来回穿越 scene1/scene3（都在 n1）30s → 登录 60/60、切场景 19、失败 0、`moveBlocked=0`。
- n1 `handoversIn=119`（100 只随搬迁过来的怪 + 19 个玩家），`handoverFails=0` 全线。
- 无地节点登录：`code=3 reason=no scene available`（干净拒绝，不 panic）。

## 遗留

- 拓扑不持久化：重启从配置重建再靠对账纠正，中间几十毫秒是"自认为主人"（网关已延后 300ms）。
- 摘要全量：O(N·S) 条消息/周期，上百节点要改成增量。
- 被退休的地上如果有玩家会被直接清掉（理论上不该发生）。
- 仍无自动重分区：对账只保证"看法一致"，不保证"看法合理"。（M3.7 已补，见下。）

## M3.7 自动重分区调度

- 新文件 `internal/world/scheduler.go`（~400 行）：组件名 `auto-rebalance`，每节点独立决策，只搬自己拥有的超载场景。
- 决策：聚合 `Chunks()` → 公平份额 `ceil(totalScenes/aliveNodes)` → 我超 `allowance+slack` 才触发 → 目标=活节点里持有最少的 → **硬条件 `target+1 < myScenes`**（防振荡）→ 候选排序：相邻 > 实体最多 > id 最小。
- 不接管死节点的地（主人可能只是分区，自动接管会和回来后的主人撞车）。
- 并发：`inflight` 一次只搬一个；判落地用 `PeerOf` 变了（成功）或超冷却仍在我手（abort），**不用 `Moving()`**（返回 nil 到 tick 处理 msgBeginMove 之间 ~1ms 窗口 Moving() 还是 false，会误清 inflight 导致连发两个搬迁）。
- main.go 加 `-auto-rebalance/-rebalance-eval/-rebalance-cooldown/-rebalance-slack`；`/admin/state` 暴露 `scheduler` 统计（evaluations/attempted/succeeded/rejected/lastDecision）。
- 新配置 `configs/world-5scene-3node.json`：n1 持 scene1/2/3、n2 持 4、n3 持 5（故意不均衡）。
- 测试 `scheduler_test.go` 6 个：主搬迁、平衡不动、inflight defer、冷却跳过、只有超载节点动、adjScore 单元。

### 实测（三节点 + file 发现，-auto-rebalance -rebalance-eval 3s，每场景 100 怪）

- 三节点互发现 +13s，n1 首次评估：`auto-rebalance move scene=3 to=n2 ents=100 from=3 fair=2`（scene3 与 n2 的 scene4 相邻）。
- 决策到退休 **190ms**（drain 100 实体 50ms + Activate + retired）；n2 `scene adopted ver=1 handIn=108`（100 搬入 + 8 穿越迁入）。
- 收敛：n1=2(scene1,2)、n2=2(scene3,4)、n3=1(scene5)，实体各 100 守恒；三节点 chunks 一致。
- 之后 5 个评估周期 `attempted` 不再增长（防振荡硬条件生效）。
- 40 bot 沿 X 穿越五场景 25s：`logined=40 failed=0 sceneSwitches=11 handoverFails=0 moveBlocked=0 avgRTT=1.9ms`。
- 三节点 `/admin/shutdown` 全部 exit 0。

### 踩坑（已写入 ARCHITECTURE 6.13 + README 约束 18-20）

- inflight 误清：用 Moving() 判落地 → ~1ms 窗口误判 → 连发两个搬迁 → 版本号连跳。改用 PeerOf 判切主。
- 公平份额把死节点数进去：死节点场景计入分母 → 活节点都"低于平均"不触发。改成只数活节点持有。
- 搬迁相邻性：按"实体最多"挑 → 把 scene1 搬到 n2 → n2 持飞地 [0,512)+[1536,2048) 路由不连续。改相邻优先后搬 scene3 → n2 持连续 [1024,2048)。
